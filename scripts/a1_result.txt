## How the qstr table is reproduced (load-bearing)
- The vendored header is a byte-identical copy of
  petitpy-orig's `vendor/micropython_embed/genhdr/qstrdefs.generated.h`
  (orig HEAD df7de3a; SHA-256 verified equal after copy).
- `build.rs` parses the header at build time (same grammar as the Zig
  comptime parser in qstr.zig: QDEF0/QDEF1 lines, hash/len/string with
  C-escape decoding, declared-len check) and emits `OUT_DIR/qstr_table.rs`
  with QSTR_STRINGS / QSTR_HASHES / QSTR_LENGTHS plus GEN_N_STATIC /
  GEN_N_MAIN. Ids are file order, exactly as the vendor MP_QSTR_* enum.
- Numbering CANNOT drift: build.rs panics if QDEF0 != 228 or QDEF1 != 385;
  qstr.rs has compile-time asserts tying N_STATIC/N_MAIN to the generated
  counts; and the Rust test `generated_table_matches_vendored_header`
  independently re-parses the vendored header and compares all 613 entries.
- Counts: N_STATIC 228, N_MAIN 385, N_TOTAL 613, QSTR_LAST_STATIC 165.

## grammar_data verification (dump-and-diff, not eyeballing)
- `scripts/check_grammar_data.py`: PASS — all 1,030 values identical
  (scalars 14, RULE_* 183, rule_act 183, combined 467, offset 183).
- Structural finding (verified against vendor py/parse.c:1098-1099):
  `get_rule_arg(id)` returns a pointer/slice at the rule's offset and
  the caller reads `rule_act(id) & RULE_ACT_ARG_MASK` entries. Rule
  spans are NOT a contiguous partition: 35 rules overlap the next rule's
  span by one entry or leave a one-entry gap (vendor RULE_PADDING enum
  construction). The port preserves this verbatim; the only invariant
  asserted is that every [offset, offset+count) lies inside the combined
  table, and the last rule's span ends exactly at 467.
- The Zig file's `// RULE_x` comments sit on the SECOND entry of some
  rules' spans (e.g. funcdef's span starts at 0x101a, the commented
  line, while the previous rule's span ends at 0x2044 one entry earlier);
  the test expectations follow the offset table, not the comments.

## qstr_test.zig — NOT ported yet (deferred to Phase B, by design)
- qstr_test.zig is a differential CLI program, not a unit-test file: it
  needs `mpy.zig` (read .mpy) + a built mpy-cross binary. Neither exists
  in the Rust port yet (mpy is Phase B) and mpy-cross is not built in
  this checkout. Porting it now is impossible, not skipped.
- Its assertions are covered in stronger form by tests 15–16 above:
  every static id resolves to non-empty bytes with self-consistent
  len/hash and re-interns to the same id; every .new literal interns
  to id > QSTR_LAST_STATIC and dedups (covered by tests 5/8/15).
- When mpy.zig lands (Phase B), the qstr_test.zig flow should be
  re-implemented as a Rust integration check against mpy-cross output.

## Divergences from the Zig original (all deliberate, documented in code)
- Dynamic entries are owned `Vec<u8>` (no 128-byte chunk slabs, no
  trailing NUL): chunk layout is an allocation detail with no observable
  behavior; ids/bytes/lengths/hashes are identical.
- `QstrEntry` is defined in qstr.rs (moves to mpy.rs in Phase B); the
  Zig original likewise defines the conversion in qstr.zig.
- `get_rule_arg` returns `&[u16]` of length `rule_act & 0x0f` instead of
  a raw `[*]const u16` pointer (vendor parse.c reads exactly that many).
- `PyError` is a minimal enum (`PyRaise`, `OutOfMemory`) + `PyResult<T>`
  alias; the full taxonomy/pending_exc transport comes with the runtime.
- RULE_* constants keep exact Zig/vendor names, so
  `#![allow(non_upper_case_globals)]` is set on grammar_data.rs with a
  justification comment (renaming would break line-by-line checkability).
  This was the only warning source (183 warnings before the allow, 0 after).

## What did NOT port cleanly
- Nothing in scope failed to port. Two self-inflicted mistakes during the
  work, both caught by tests before commit:
  a) build.rs used `decoded.len` (field) instead of `decoded.len()`.
  b) A spot-check expectation for RULE_funcdef was written from the Zig
     file's misleading `// RULE_funcdef` comment line (0x2044) instead of
     the offset table (0x101a); the test caught it, and the offset table
     (verified by dump-and-diff) was confirmed correct.
