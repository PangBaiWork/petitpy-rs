## QstrEntry migration (anticipated by A1)
`QstrEntry` moved from `qstr.rs` (borrowed `&[u8]`) to `mpy.rs`
(owned `Vec<u8>`), matching the Zig original where the type is
`mpy.QstrEntry` and `qstr.zig` only holds the conversion.
`qstr.rs` re-exports it (`pub use super::mpy::QstrEntry;`) so the
`qstr::QstrEntry` path keeps working, and `QstrContext::to_entry`
now returns the owned form (one small allocation per call; the
emitter calls it once per qstr). Only `qstr.rs` used the type
(verified by grep), so nothing else changed.

## runtime/qstr.zig vs compiler/qstr.zig — disagreement checked
The brief asked to report any disagreement between the two qstr
implementations. Finding: **no behavioral disagreement — but stale
comments in runtime/qstr.zig.** Its header comment and the comments
on lines 212-214 claim N_MAIN = 216 / N_TOTAL = 444, while the
compiler side has N_MAIN = 385 / N_TOTAL = 613. The code in BOTH
files parses the SAME generated header
(`vendor/micropython_embed/genhdr/qstrdefs.generated.h`, 385 QDEF1
lines — both build.zig `qstrdefs_h` imports point at it), so at
build time both must compute 385/613. Proved by execution, not just
reading: a probe binary importing `runtime/qstr.zig` (Zig 0.16
`-M`/`--dep` wiring, /tmp/qstr_probe.zig) printed
`runtime N_TOTAL=613`, `qstr_str(500)=modf`,
`qstr_str(612)={:#b}`. Root cause of the stale comment: the QDEF1
count grew over time (qstr.rs documents the bumps: 216 -> 227 (JS) ->
229 -> ... -> 385); the runtime comments were never updated. No
action needed for the .mpy port (the reader stores raw ids and never
resolves them); flag for Phase C so the comments get fixed with the
runtime qstr port.

## Divergences from the Zig original (all deliberate, in code + here)
- Owned data: Zig returns allocator-owned slices (`gpa.dupe`); Rust
  stores `Vec<u8>`/`Vec<_>`. No `deinit` — `Drop` frees everything.
- `RawCode.kind` is `u8`, not Zig's `u2`. The reader reproduces
  Zig's `@intCast` truncation (`(kind_offset + 2) mod 4`); the writer
  uses `wrapping_sub` + `debug_assert!` (mirrors Zig Debug panic vs
  ReleaseFast wrap; only the low 2 bits reach the header either way).
- `write` is infallible (`Vec<u8>`) where Zig returns
  `Allocator.Error![]u8` — Rust `Vec` push has no fallible spelling.
  The reader keeps the fallible shape via `try_reserve` ->
  `MpyError::OutOfMemory` (same treatment as qstr.rs). On absurd
  counts (e.g. n_qstr = 2^60) Rust returns OutOfMemory where Zig
  returns Allocator.Error — same outcome, different spelling.
- `read_bytes` uses `checked_add` for `len + 1` (qstr/str/bytes):
  overflow maps to `UnexpectedEof`, which is also what the bounds
  check would produce — no observable difference on any real input.
- The `mpy-roundtrip` example accepts an optional 2nd argument
  (output path for the re-serialized bytes) that the Zig CLI lacks;
  with one argument its messages/exit codes are exactly the Zig
  CLI's. It exists so the write check can feed Rust-written .mpy
  files to `petitpy-vm`.

## Format edge — empty-children header (property of the format)
A raw-code header with `has_children` set but `n_children == 0`
parses to an empty children list, and the writer derives
`has_children` from `children.len() > 0`, so re-serialization drops
the bit (8 bytes in, 7 out, first diff at offset 6). The Zig writer
does exactly the same (`writeRawCode`: `has_children =
rc.children.len > 0`), and the Zig round-trip tool reports MISMATCH
on those bytes too (verified in check_mpy_write.sh). The compiler
never emits such a header. Covered by a Rust unit test + the script.

## Original bugs observed (not mine to fix; recorded for the record)
- Complex constants are broken at RUNTIME in the original: `print(4j)`
  and `c = 1j` fail with `ValueError: invalid syntax for number`
  (rc=1); `complex(3, 4)` makes the original binary PANIC
  (SIGABRT, rc=134, `mp_mirrors.zig:745 fromPtr` null-pointer cast).
  The .mpy FORMAT handles complex consts fine (complex.py emits a
  valid 109-byte .mpy; Rust round-trip byte-identical; dump-agree).
  complex.py is therefore a format-only sample: both the .py run and
  the Rust-written .mpy run fail identically (rc=1, same message).
- Error-stream difference between the original's own execution paths:
  the .py path reports the ValueError on stderr, the .mpy path on
  stdout. Not a format issue; the write-check script compares
  combined output for this case and notes the difference.
- `petitpy file.mpy` does NOT run .mpy files (parses bytes as Python
  source -> SyntaxError); `petitpy-vm` is the .mpy runner.
