## @cImport finding (the brief's premise was WRONG — verified by grep)
- `lexer.zig` has NO `@cImport`: the only occurrence is the header
  comment "1. No @cImport. The `mp_token_kind_t` enum is mirrored
  locally as `TokenKind`…". The earlier grep that listed lexer.zig
  matched that comment.
- `lexer_test.zig` DOES use `@cImport`, but only for libc
  `unistd.h`/`stdlib.h`, used for `libc.write` (fd 1/2 output) and
  `std.process.exit` — both plain Rust std (`std::io::Write` /
  `std::process::exit`) in the port. No C FFI anywhere, nothing
  load-bearing: there is no C table or constant to reproduce.
- `lexer.zig` imports `build_options` (Zig build option) for one
  bool: `STR_UNICODE` (default on, build.zig:364 `orelse true`).
  Reproduced by extending `build.rs` to emit `build_options.rs`
  into OUT_DIR with `pub(crate) const STR_UNICODE: bool`, read from
  `PETITPY_STR_UNICODE` (default true); `lexer/mod.rs` includes it.
  Verified: the corpus diff below runs with STR_UNICODE=true.

## lexer_test.zig — NOT ported as a CLI (same reason as A1's
## qstr_test.zig, by design)
- It is a differential CLI program, not unit tests: it spawns a
  `token_dump` binary that does not exist anywhere (see above) and
  diffs its output against the Zig lexer's dump. Porting it now
  would reproduce a harness for a binary that was never built.
- Its assertions are covered in stronger form by the zigdiff check:
  every corpus file's full token stream (kind + line + column +
  vstr bytes) matches the Zig lexer's, which is exactly what
  lexer_test.zig was built to prove.
- The `examples/lex_dump.rs` binary IS the Rust spelling of its
  `dumpZig` (same wire format, same stop conditions: break after
  END/INVALID, continue past DEDENT_MISMATCH/LONELY_STRING_OPEN),
  so the Zig-side flow can be re-implemented against it if a vendor
  token_dump ever appears.

## Divergences from the Zig original (all deliberate, documented in code)
- Layout split: one 1,436-line Zig file became `lexer/` (mod +
  tables + chars + string + peek + tests) because the project rule
  caps every .rs file at 800 lines. Module path from outside is
  unchanged (`crate::compiler::lexer`); `impl Lexer` blocks live in
  the submodules, which can see the struct's private fields.
- `Reader` is a trait object (`Box<dyn ByteSource>`) instead of two
  fn pointers + `*anyopaque`; the slice reader OWNS a copy of the
  source (`Vec<u8>`) instead of borrowing it, so the Lexer carries
  no lifetime parameter. Token streams, positions and errors are
  identical; the copy is an allocation detail.
- `LexError` is a local enum (`UnicodeNameEscape`, `OutOfMemory`)
  mirroring Zig's local `StringParseError` set (deliberately NOT
  `PyError`, as the Zig file documents). `OutOfMemory` is
  unreachable in practice: Rust allocation failure aborts where Zig
  would propagate the error — observable difference only under
  actual OOM.
- No `lexerFree`: Rust `Drop` calls `reader.close()` (mirroring
  lexerFree's close call); the Vecs drop automatically.
- Keyword lookup does not append a NUL to the vstr: `strcmp_slice`
  treats the end of each slice as the NUL, exactly equivalent to C
  strcmp on the NUL-terminated copy the Zig side builds (and pops).
- `source_name` is carried but never read by the lexer (same as
  Zig); the field has `#[allow(dead_code)]` with a comment — the
  parser (A3) will read it. This was the only warning source.
- `TokenKind` keeps Zig/vendor SCREAMING_SNAKE variant names with a
  file-level `#![allow(non_camel_case_types)]` (same precedent as
  A1's `non_upper_case_globals` allow); renaming would break
  line-by-line checkability and the `@tagName` spellings used by
  the dump. `TokenKind::from_u8` replaces `@enumFromInt`;
  `TokenKind::name()` replaces `@tagName`.
- `indent_push` uses `u16::try_from(...).expect(...)` (mirrors Zig
  `@intCast` panicking on overflow in debug mode); the Zig
  alloc/num indent bookkeeping is a `Vec<u16>` with the bottom
  entry always 0.
- `f'{a=}'` / `f'{{}}'` expectations were first written wrong from
  intuition (`"{a=}"`, `"{}"`) and the tests caught it: the real
  vstr values are `"a={}"` and `"{{}}"` (the format string, not the
  formatted result). Fixed before commit.

## What did NOT port cleanly
- Nothing in scope failed to port. Three self-inflicted mistakes
  during the work, all caught by tests before commit:
  a) `keyword_table_lookup` expected `__debug__` to stay
     KW___DEBUG__, but the lexer (like Zig) flips it to KW_TRUE
     under debug_mode=true. Test fixed, lexer was right.
  b) `lex_dump` used `writeln!` for the token prefix, putting the
     hex bytes on a separate line — the zigdiff run caught it
     (streams diverged on every file). Fixed to `write!` + trailing
     `writeln!`; zigdiff then passed 552/552.
  c) `check_lexer_zigdiff.py` deleted its own `run()` helper in one
     edit (NameError); restored. Also fixed in the same script: Zig
     0.16 API drift — `b.path()` rejects absolute paths (header now
     copied into scratch), `std.process.argsAlloc` gone (use the
     `main(init)` + `init.minimal.args` pattern from main.zig),
     `std.fs.cwd()` gone (use `std.Io.Dir.cwd()` +
     `readFileAllocOptions` / `writeStreamingAll` from main.zig),
     `ArrayList.writer` gone (use `allocPrint` + appends),
     `c_allocator` needs libc (use `init.gpa`).
     Note for later phases: `lexer_test.zig`'s TBD "Zig 0.16 API
     translations" are exactly these four renames.
