## §2. The four mechanisms (all vendor hooks, no new Rust types)

### (a) Type subscript → `typing._class_getitem` — `src/runtime/vm_seams.rs`
###     (`typing_call_ctx` + `try_instance_subscr` widening)

Vendor: `obj.zig:600-614` (`mpObjSubscrImpl`): after the type's
subscr slot declines, on full, a Get on an exact-type base calls
`typingCall(MP_QSTR__class_getitem, base, index)`; `typingCall`
(`runtime.zig:538-545`) imports `typing` and calls the named
attribute with two args.
Rust: new `typing_call_ctx(ctx, state, name, a, b)` — the VM-path
`typingCall` (real `import_name_ctx` + `load_attr_ctx` +
`call_function_ctx`, so the callee is the frozen Python, not a
Rust re-invention). The branch lives in `try_instance_subscr`:
the LOAD_SUBSCR call site is in `vm_dispatch.rs` (the F3 lane's
file — not touched), and the slot path (`obj_subscr`) is a pure
`CallCtx` function with no import/call access, so the VM-hook
path is the only place it can live. Guards, exactly as the
vendor: Get only; base's header type is exactly `type`; the
base's type (its metaclass) has NO subscr slot (the vendor tries
the slot first — a metaclass `__getitem__` falls through to
`obj_subscr`). `type_type_data` has `subscr: None`, so plain
classes and builtin types take the branch.
`_class_getitem` (frozen typing.py) builds `GenericAlias(cls,
item)` when the class has no own hook, and calls the class's own
`__class_getitem__` when it does (`G[int]` → `('G', <class 'int'>)`).
Its `type(f) is _bound_method` check works: `type(g.__repr__)`
is `<class 'bound_method'>` on both binaries (probed).

### (b) Type `|` → `typing._union` — `src/runtime/vm_rt.rs`
###     (`binary_op_ctx` + `is_type_or_none`)

Vendor: `runtime.zig:575-578` (`mpBinaryOpImpl`): on full, op ==
`MP_BINARY_OP_OR` with both sides a type or None
(`isTypeOrNone`: `None` or exact `type`) and not both None →
`typingCall(MP_QSTR__union, lhs, rhs)`, BEFORE the small-int
path and BEFORE `nativeSubclassOp`.
Rust: the same branch at the old stub comment in
`binary_op_ctx` (which said "fall through to `binopUnsupported`
until then"), using `typing_call_ctx`. `_union` (frozen
typing.py) flattens nested unions, dedups preserving order, and
returns the single member itself (`int | int` → `<class 'int'>`).
`list[str] | None` needs no special case: `GenericAlias.__or__`
is plain Python (`_union(self, o)`) once (a) works. `int | 5`
and `None | None` do NOT take the branch (one side is not
type-or-None / both None) and raise the vendor's
`binopUnsupported` message (`unsupported types for __or__:
'type', 'int'` — probed byte-identical).

### (c) `isinstance` / `issubclass` with a UnionType — `src/objects/objtype/subclass.rs`
###     + `src/objects/objtype/seams.rs` (`real_load_maybe` members step)

Vendor: `objtype.zig:514-549` (`unionArgs` + `isSubclassImpl`):
a classinfo WITH `__origin__` (a generic alias) is NOT a union;
else its `__args__` tuple (if a tuple) is the classinfo tuple.
Rust already had `union_args` + the `is_subclass` union branch —
it was dead because the builtin adapters used `with_stub_seams`
whose `load_maybe` always returns None. Fix, two halves:
1. `isinstance_builtin` / `issubclass_builtin` now use
   `with_seams(real_load_maybe, ...)` instead of stub seams.
2. `real_load_maybe` reads the instance members map BEFORE
   `class_lookup`: the vendor's `mp_load_method_maybe`
   (`runtime.zig:1195-1229`) calls the type's attr slot before
   the locals_dict search, and for a user instance that slot
   reads the members map first (`instance_load_attr` step 1).
   Without this, a UnionType's `__args__` tuple — an instance
   member — was invisible and `isinstance(1, int | None)` fell
   through to `IssubclassArg2`. Members are returned RAW,
   unbound (`(value, None)` — an instance-dict function is not
   bound, as in MicroPython/CPython). This also makes the
   `__reversed__` / `__len__` / `__iter__` probes see an
   instance member of the same name, as the vendor does (it
   returns the member and the caller then fails to call it,
   instead of silently falling through) — full gate stayed
   GREEN, so no corpus program is affected.
A generic alias still raises the arg-2 TypeError: its
`__origin__` member makes `union_args` return `None`
(`isinstance(1, list[int])` — probed byte-identical).

### (d) `isinstance` / `issubclass` arg-error messages — `subclass.rs`
###     (`record_typed`, pre-existing gap fixed in passing)

The adapters returned only `e.to_pyerror()` without recording
the typed raise, so the VM built a bare `TypeError` with an
empty message. Verified pre-existing on base master:
`isinstance(1, 5)` and `issubclass(1, int)` both raised bare
`TypeError: ` on fdd1fc1. Now `.map_err(|e| ctx.record_typed(e))`
(the `make_new.rs` precedent; `TypedRaise` for `ObjTypeError`
landed in F4), so both messages match the reference
(`issubclass() arg 1 must be a class` /
`issubclass() arg 2 must be a class or a tuple of classes`).
`BareTypeError` still records nothing (empty name) — same as
before, only reachable while bootstrapping.

### (e) `get_type_hints` — no Rust change

The frozen `get_type_hints` runs as plain Python; every runtime
behaviour it leans on already worked and was verified by probe
on both binaries: `__annotations__` in the class dict (stored
as source strings — `x: int` → `'int'`, `y: "list[str]"` →
`"'list[str]'"`, so the double `eval` in typing.py is needed),
`__bases__`, `__module__` (`__main__` for script classes —
needed for `list[__main__.A]` too), `sys.modules.get("__main__")`
→ `None` (sys.modules is empty at script start) with the
`__import__("__main__")` fallback, and `eval(v, g, l)` with
explicit globals/locals. The integration case's final line
matches byte-for-byte.

## §4. Left open

- `type('T', (B,), {})`-style metaclass class creation is
  limited on the reference itself (see meta.py above) — not
  an F5a gap, recorded only because the probe was run.
- The `InplaceOr` (`|=`) form on types does NOT take the
  union branch (the vendor checks `MP_BINARY_OP_OR` only in
  `runtime.zig:575-578`; the Rust generic loop converts
  inplace→plain later, but the branch sits before the loop).
  Probed on both binaries: `x = int; x |= str` raises
  `TypeError: unsupported types for __or__: 'type', 'type'`
  and `x |= None` raises `... 'type', 'NoneType'` — identical.
  Deliberate vendor fidelity, not a gap.
- `real_load_maybe` still has no `__class__` / `__next__`
  special cases from `mp_load_method_maybe`
  (`runtime.zig:1199-1210`) — no caller needs them yet.
