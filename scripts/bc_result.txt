2. Encode reuse — emit side vs runtime side (brief: compare first)
---------------------------------------------------------------------
IDENTICAL algorithm, verified by hand and by test. Zig
`mp_encode_uint`: fills a 10-byte buffer from the end with plain
`val & 0x7f` chunks, then copies out setting `| 0x80` on every byte
but the last. Emit `encode_uint` (Phase B, `emit/encoders.rs`):
fills from the end setting `| 0x80` while filling, leaving the
least-significant chunk clear. Same bytes for every input,
including 0 (one `0x00` byte) and `usize::MAX` (10 bytes).
`DUMMY_DATA_SIZE` (emit consts.rs) == `MP_ENCODE_UINT_MAX_BYTES`
== 10. Therefore the runtime module **re-exports** the emit
encoder (`pub use crate::compiler::emit::encoders::encode_uint`)
and defines no second encoder. Decode is new here; the cross-check
test encodes with the emit encoder and decodes with the runtime
decoder for 10 boundary values (0, 1, 127, 128, 300, 16383,
16384, 2^28, 2^56, usize::MAX) against hand-computed byte
vectors — same value, same bytes.
Difference in API shape only: Zig takes a C allocator callback;
Rust takes `&mut [u8]` and returns the written slice (the emit
port's shape, kept as-is).

3. MpCodeState — Rust shape
----------------------------
```rust
pub struct CodeState {
    pub fun: GcRef,                  // fun_bc (Obj::FunBc slot)
    pub ip: usize,                   // byte offset into RawCode.fun_data
    pub state: Vec<Option<Value>>,   // n_state slots; None == MP_OBJ_NULL
    pub n_state: usize,              // caller-decoded, cached
    pub exc_sp_idx: usize,           // 0 after setup
}
```
Only the fields bc.zig uses. NOT stored, by design (see bc.rs
module docs): C `sp` (`&state[0] - 1`) — the VM's value-stack
pointer, owned by the VM lane (C13); `old_globals` — set by the C
caller (`INIT_CODESTATE`, objfun.c:217-220) *after*
`mp_setup_code_state` returns.
The three `mp_obj_fun_bc_t` pieces the helper reads are passed
explicitly, because the frozen `FunBcData` (value-obj-design D4)
holds only a code-store index: `code: &RawCode` (fun_data =
prelude + source info + cells + bytecode), `qstr_table: &[u16]`
(the module's resolved qstr table, as the C loader builds it
from the .mpy qstr section), `extra_args: &[Value]` (creation
order: n_def_pos_args positional defaults, then the defkwargs
dict iff DEFKWARGS — `mp_obj_new_fun_bc`, objfun.c:414-440).
`n_state` is a caller parameter, as in C (the caller decodes it
from the sig prelude, `DECODE_CODESTATE_SIZE`; the helper
decodes S again only to discard it).
`empty_tuple: Value` is a parameter: the original stores the
`mp_const_empty_tuple` singleton for the empty-`*args` case
(objtuple.c:241-243), and the reference binary proves the
identity is observable (`def f(*a): return a is ()` → True);
a fresh empty tuple per call would break it. The VM owns the
singleton and passes it in.
Raises become `Result<CodeState, SetupError>`: the exception
object lives in `VmState.pending_exc` (D7) which does not exist
yet, so the error carries exactly the data the original formats
into its TypeError (arg index / qstr id); `SetupError::message`
renders the TERSE strings.

4. Decisions / equivalences worth recording
--------------------------------------------
- `map_lookup` is a linear scan over `DictData.map.entries`
  (the C map is a hash table; same lookup semantics — C9 owns
  the payload and may replace it). It returns `(index, is_new)`:
  `is_new` is exactly the C test `elem->value == MP_OBJ_NULL`
  on a fresh `ADD_IF_NOT_FOUND` insert, because a stored value
  is never NULL (the placeholder is `Value::None` and is set by
  the caller immediately). This matters: a stored Python `None`
  must NOT look like a fresh entry (dict-path duplicate kwargs
  with a `None` value still raise).
- `kwargs = args + n_args` is computed BEFORE the positional
  check reassigns `n_args` (bc.c/bc.zig order); the Rust code
  splits `args` up front (`pos_args`, `kw_pairs`) to keep that
  order explicit.
- The defaults-fill loop and the mandatory-positional check
  reproduce the C pointer arithmetic exactly, including the
  `*d++ == NULL` post-increment: the reported number is
  `n_state - d` AFTER the increment, i.e. the 0-based arg index
  (verified on the binary: f(a, b=2) called as f(b=3) → #0;
  f(a, b, c=3) called as f(c=4) → #1).
- `decode_uint` uses `wrapping_shl`, matching C unsigned wrap
  for over-long varints (Zig `<<` on usize wraps the same way).
- Truncated bytecode panics (slice indexing), mirroring the Zig
  port's index-out-of-bounds panic on the same malformed input.
- Rooting: allocations inside setup use the caller's `RootSet`.
  With the C0 skeleton's threshold of -1 no collection can
  trigger mid-setup; once C4 lands the trigger rule the VM must
  root the in-progress code state, as it roots its value stack.
- `prelude_sig_decode` / `prelude_size_decode` (+ their structs)
  are `pub(crate)`: the VM lane needs the sig decode itself to
  size the code state (`DECODE_CODESTATE_SIZE`), and the tests
  pin the decode vectors.
