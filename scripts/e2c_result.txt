1. `list.sort(key=<python fn>)` — `list_sort` (E2 §4 (c)).
   `list_sort_builtin` (`objlist_methods.rs`) is ctx-only, so a
   FunBc key could not run through it. Same hook-threading as
   `sorted` (E2b `VmHook`): new `VmState.list_sort_builtin`
   field (the `sort` method object, looked up by name in the
   list type dict at startup in `vm_builtins_bind.rs`, the
   join-lookup pattern), intercept arm in
   `vm_call_intercept.rs` → new `call_list_sort_ctx` in
   `builtin_vm.rs`. `sort_with_key` refactored into
   `sort_items_with_key` (returns the sorted items) + a thin
   wrapper; `call_list_sort_ctx` parses key/reverse, decorates
   via `call_function_ctx`, sorts, writes the items back into
   the original list's arena payload in place, returns None.
   None key delegates to the plain `list_sort_builtin`.
   The original's keyed sort calls the key PER COMPARISON
   inside an in-place quicksort and ABORTS (rc=134) when a
   key call or comparison fails (probed: `l.sort(key=len)` on
   ints, `[3,'a',1,2].sort(key=lambda x: x)`); Rust
   decorates once + stable-sorts and raises instead —
   result-identical for pure keys, documented divergence.
   6 tests. All `key=` / `reverse=` lines in `list_sort.py`

2. `pow(0, 0)` — builtin (E2 §4 (d)). Root cause: the
   vendor's `mp_builtin_pow` 2-arg form IS
   `mp_binary_op(POWER)` (modbuiltins.c:369); small-int
   pairs take the ans=1 loop (`mp_small_int_binary_op`,
   runtime.c — `0**0=1`), while the slot path uses mpz
   semantics (`pow_inpl` returns 0 for a zero base).
   Probed reference: `pow(0,0)==1`, `pow(z,0)==1` (z =
   heap-int-valued zero), `pow(0,0,5)==0`, `0.0**0==1.0`,
   `pow(0,-1)` → ZeroDivisionError both. Fix in
   `builtin_fns.rs` `pow_impl`: the 2-arg form routes
   SmallInt×SmallInt pairs through `small_int_binary_op`
   (existing pub(crate) helper in `runtime_smallint.rs`),
   with a pre-check excluding `lv==0 && rv<0` (the only
   error that path returns; the slot path already raises
   ZeroDivisionError there) and `GoGeneric` falling through
   to `binary_op_plain` with the heap-converted lhs. 5
   tests. `builtin_pow3` / `builtin_pow3_intbig` already
   passed at E2 (the `pow(0,0)` case is probe-only); all
   probe lines now byte-identical to the reference.

7. `map()` / `filter()` / `zip()` / `enumerate()` over a
   generator iterable (E2b gap). Root cause (first
   found): C11's `iternext` (`iters/iter.rs`) only
   accepts `Obj::Iterator` — a generator sub-iterator
   returns `Err(TypeError("object not an iterator"))`.
   Baseline probes confirmed map, filter AND zip over a
   genexpr all fail with bare TypeError on Rust while
   the reference returns values.
   Design (after hitting E0524 then E0503): `IterSeams`
   gained TWO new fields — `next: Option<&mut dyn
   FnMut(&mut CallCtx, Value) -> CallOutcome>` (resume
   closure; C14 runtime supplies `resume_gen`) and
   `next_builtin: Option<Value>` (the `next` builtin
   object; VM supplies `state.next_builtin` — calling it
   through the existing `call` seam routes via the
   intercept to the real resume, avoiding a second
   `&mut VmState` borrow, which the borrow checker
   rejects: two closures over `state` → E0524; reading
   `state.next_builtin` after the call seam is built →
   E0503, fixed by copying it out before the closures).
   New `next_sub` helper in iter.rs: Obj::Iterator →
   C11 `iternext`; else `next` closure if present; else
   `next_builtin` via the `call` seam (Value→Some,
   Stop→None, Raise→Err(PyRaise)); else NOT_AN_ITERATOR
   (exact old error). Pull sites switched to `next_sub`:
   objmap.rs:93, objfilter.rs:72, objzip.rs:81,
   objenumerate.rs:114. All 15 `IterSeams {`
   construction sites updated (4 production:
   objdict_collect.rs:290 `next: None, next_builtin:
   None` — ctx-only, preserves old behavior;
   make_new.rs:260 reversed stubs, both None;
   runtime_iter.rs:192 `next: Some(resume_gen closure),
   next_builtin: None`; vm_rt_iter.rs:177 `next: None,
   next_builtin: Some(next_builtin)` — copied out
   before the closures; 11 test sites, both None).
   First failure round: the 9 item-7 tests were
   initially written with tautological placeholder
   assertions — rewritten with real bool-equality
   assertions plus filter/zip/enumerate/two-iters/
   nested-map/unpack/raises cases. They then ALL failed
   with a bare TypeError, because `list()` goes through
   `collect_iterable`'s `IterPlan::Protocol` arm
   (objdict_collect.rs), NOT through `iternext_vm_ctx`
   — the Protocol arm builds its own seams with
   `next: None, next_builtin: None`.
   Second round (wrong fix, then reverted): a
   `fun == nb` identity check in the Protocol arm's call
   seam + new `VmHook::next_builtin()` /
   `VmHook::take_stop_iteration()` trait methods was
   implemented to classify a StopIteration from the
   `next` builtin as exhaustion. It made zip/enumerate
   pass but map/filter still failed with a bare
   TypeError, because C11's `iternext` dispatch
   (`extra.len() == 2` branch) only recognises an
   `Obj::Iterator` sub — a map-1/filter-1/zip-1 over a
   generator has `extra = [TAG, gen]` (len 2) and
   `second_is_iter` was false → NOT_AN_ITERATOR. Fix
   applied and KEPT: `second_is_iter` in `iter.rs` now
   also matches `Obj::Generator` (range `[stop, step]`
   and enumerate's counter in `extra[1]` are SmallInts,
   so unaffected; getitemiter is len 1). After that,
   all 9 tests passed — but a probe of the edge case
   `list(map(next, [x, x, x]))` (same generator three
   times) showed the identity check is WRONG: reference
   raises StopIteration, Rust gave a bare TypeError
   (because `map_iternext` maps the call seam's `Stop`
   to `PyRaise`, and the stashed exception had been
   drained by `take_stop_iteration`). The `fun == nb`
   check cannot distinguish `next_sub`'s call (generator
   exhaustion → end the map) from `map_iternext` calling
   `f == next` as the mapped function (StopIteration
   from `next(gen)` → must RAISE). No `map(next,...)`
   exists in the corpus/tests, but the divergence was
   real and the mechanism was wrong.
   Final fix (KEPT): reverted the `fun == nb`
   classification and the `VmHook::next_builtin` /
   `take_stop_iteration` trait methods + impls entirely.
   The Protocol arm now shares ONE hook between the
   `call` seam and a real `next` seam through a
   `RefCell` (`hook_cell = RefCell::new(call.as_deref_
   mut())`): the `next` seam is a plain closure local
   `next_fn` calling `hook.resume(ctx, sub)` (the
   `iternext` form — `Ok(None)` = exhaustion →
   `CallOutcome::Stop`, a raise → `Raise`), and the
   call seam borrows the same cell. Two closures over
   the same `&mut` hook cannot be built (E0524 — the
   E2b `VmHook` rationale), so the `RefCell` is the
   standard sharing mechanism; the two seams are only
   ever called sequentially by C11's `iternext` (pull
   subs, then call the function) and a nested collection
   builds its own hook and cell, so `borrow_mut` cannot
   panic re-entrantly (documented in the code comment).
   A first attempt using `Option<Box<dyn FnMut>>` +
   `as_deref_mut()` failed with E0597 (the Box's
   destructor tripped drop-order analysis); the
   plain-closure local compiles. Without a hook the
   `next` seam records `TypeError("object not
   iterable")` itself and returns `Raise`, so the
   ctx-only error is unchanged. Verified:
   `list(map(next, [x,x,x]))` now raises StopIteration
   exactly like the reference; all item-7 cases
   (`['1','2']`, `[2]`, `[(1,3),(2,4)]`, `[(0,1),(1,2)]`)
   match the reference. 9 tests.

## §4 — Remaining shortfalls (per-case root cause)

(a) `list_sort` user-class ordering: `l.sort()` on
    `[A(5), A(2), …]` with `__lt__` raises `TypeError:
    unsupported types for __lt__: '', ''`. `sort_less`
    (`objlist_methods.rs`) compares via ctx-only
    `obj_binary_op` → `call_binary` → the slot
    `instance_binary_op_slot`, whose seams are STUB
    seams, so `seams.call_pair` on the FunBc `__lt__`
    fails → `Ok(None)` → `PyRaise`. Top-level `A(5) <
    A(2)` works (the VM's `binary_op_ctx` has the real
    hook). Fix needs a `VmHook.binary_op` (or
    comparison seam) threaded through BOTH sort paths
    (`list_sort` + `sorted`'s `sort_items_with_key` —
    `sorted([A(5), A(2)])` fails identically). Same
    class as E2 cluster (n); out of E2c scope.
(b) Container repr does not dispatch user `__repr__`:
    `print([A()])` shows `[<A object at 244>]` on Rust
    vs `[A!]` on the reference, while top-level
    `print(A())` / `repr(A())` work. The container repr
    path (list/tuple/dict) does not go through the
    instance repr dispatch E2's Fix C wired at the top
    level. Separate mechanism from (a); out of scope.
    (a)+(b) together are why `list_sort.py` still fails
    even though item 1's `key=` mechanism is fixed.
(c) `obj_binary_op` / `obj_unary_op` reflected fallback:
    internal callers (`sort_less`, `seq_cmp_objs`
    element comparison) raise `PyRaise` on
    `SlotOutcome::NotImplemented` instead of trying the
    reflected op. Needs the VM hook at those call sites
    (same threading as (a)).
(d) Integration `builtin_keyword_args`: kwargs to
    BUILTIN METHODS (`split(maxsplit=)`,
    `replace(count=)`, `pow(mod=)`, `print(sep=,
    file=)`) — a different mechanism from item 6's
    `**`-dict key interning (which only covers user
    functions). Out of scope.
(e) Integration `str_join_bytes_bytearray`:
    `b'-'.join([bytearray(b'a'), b'b'])` — bytes.join
    does not normalize bytearray elements. Different
    mechanism from item 7's generator join. Out of
    scope.
