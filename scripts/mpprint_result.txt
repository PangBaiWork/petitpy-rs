DIVISION OF LABOUR WITH objstr_print.rs (the C8c unification)
--------------------------------------------------------------
C8b's `objstr_print.rs` already held the vendor C cores
(`print_strn` / `print_mp_int` / `print_float`) in Vstr-bound
form. This lane moved the three algorithms into `mpprint.rs` ONCE
as sink-generic cores (`print_strn_core` / `print_mp_int_core` /
`print_float_core`, over `&mut dyn PrintSink`, returning the
`c_int` char count the Zig returns) and left thin wrappers in
`objstr_print.rs` with IDENTICAL signatures (the count is
discarded there, as C8b's versions did). `PF_FLAG` constants,
`IntValue`, `int_value`, and `print_float_pct` stay in
`objstr_print.rs` untouched; `mpprint.rs` re-exports the flags as
`PF_FLAG_*` so the print layer has one import site. The
refactor is behaviour-preserving by construction (same code, only
the sink parameterised) and verified by the full suite: all 440
baseline tests pass unchanged, including every C8b %-format /
str.format probe test in tests_d, plus a new test pinning three
C8b probes through the `Print` API (`c8b_probes_through_print_api`).
No call sites were rewired (brief item 6): the vsp helpers in
objstr_print.rs / objstr_format.rs keep calling the Vstr
wrappers; the `Print`-based exports have no production callers
yet — C13 wires them into the print machinery.

KEY FINDINGS (verified by the executor, main agent to re-verify)
---------------------------------------------------------------
1. BRIEF CORRECTION — `mp_plat_print` is NOT deferred: the brief
   said the stdout platform function is C13/Phase E's job, but
   the Zig shows it is a plain `write(1, ...)`
   (`vendor_stubs.zig:22-24` → `support/output.zig:16-19`, which
   discards the `write` return; no `\r\n` cooking on this
   platform). `MP_PLAT_PRINT` is therefore implemented as a plain
   stdout write, I/O errors ignored, exactly as the C does — and
   `MP_STDERR_PRINT` as a plain `write(2, ...)` (the Zig comment
   confirms no flush is needed with `write(2)`). What REMAINS
   C13/D territory is the full build's `print()`, which goes
   through `mp_sys_stdout_print` (`sys.stdout`), not this const.
2. `mp_print_int` TRUNCATES: `INT_BUF_SIZE` is 32
   (`sizeof(isize) * 4`, vendor `mpprint.c:151`), and both the C
   loop (`while (b > buf && x != 0)`) and the Zig loop
   (`if (!(b > 0 and x != 0)) break`) stop when the buffer fills.
   A base-2 `usize::MAX` prints its LOW 32 bits (`"1" * 32`).
   Ported verbatim; pinned by `mp_print_int_truncation_base2`.
   No live Zig caller exists (grep: zero callers outside
   mpprint.zig) — it is exported for C/mp_printf use.
3. `formatFloatRepr` digits: Rust's `{:e}` and Zig's Ryu `{e}`
   both emit THE shortest round-trip digit string, so they agree
   digit-for-digit (probed with rustc: `2.5→2.5e0`, `0.0→0e0`,
   `1e16→1e16`, `5e-324→5e-324`, `123456789.0→1.23456789e8`).
   The exponent is re-emitted normalised (`e±NN`, two digits
   minimum), so no source spelling can leak through.
4. The binary's `repr()` IS this branch: probed on the reference
   binary — repr(2.5)='2.5', repr(1e16)='1e+16',
   repr(1.5e-5)='1.5e-05', repr(0.1)='0.1', repr(5e-324)='5e-324',
   repr(1234567.0)='1234567.0', repr(sqrt(2))='1.4142135623730951'
   (shortest digits …951, NOT the vendor APPROX …952 the Zig
   comment warns about). The `.0` on 1234567.0 is the
   `ALWAYS_DECIMAL` framing in `mp_print_float`, not the repr
   function itself — pinned by the `mp_print_float_repr` test
   (bare branch gives '1234567', +ALWAYS_DECIMAL gives
   '1234567.0').
5. The `prec == 99` branch has NO live Zig caller today: the
   only `mp_print_float` callers are the vsp format helpers
   (objstr.zig:1798/1802, spec prec, never 99). The float print
   slot lives in vendor C (objfloat.c — C18's carve-out), so C18
   wires the repr path. The branch is ported verbatim anyway.
6. `mp_print_mp_int`'s non-int conversion: the Zig does
   `if (!objIsInt(x)) x = smallInt(mp_obj_get_int(x))`. The Rust
   version goes through C8b's `int_value` (heap big-int first,
   then the `IntMaybe` slot), which covers both arms; a value
   with no conversion returns `StrError::Obj
   (ObjError::IntConversion)` — the Zig's `mp_obj_get_int` raise
   (`TypeError: can't convert to int`, obj.rs:180). This needs
   `CallCtx` + `BuiltinTypes`, so the Rust signature gains two
   parameters over the Zig's — documented in the code.

DESIGN DECISIONS
----------------
- `PrintSink` trait (`emit(&mut self, &[u8]) -> Result<(), StrError>`)
  instead of `&mut dyn fmt::Write`: the print layer emits RAW
  BYTES (bytes objects, `%c` with `\xff`), which `fmt::Write`
  (`&str`-only) cannot carry. `Vec<u8>` and `Vstr` implement it;
  a `PrintT` implements it by calling its fn pointer. The
  existing `fmt::Write` machinery (`obj_print_helper`, print
  slots, `VstrSink`) is untouched.
- The shared cores take `&mut dyn PrintSink` and return the
  `c_int` char count; Vstr wrappers discard it. A `Vstr` sink
  still propagates its `StrError` (fixed-buffer / allocation);
  stdout/stderr sinks ignore I/O errors, as the C does.
- `PrintT` keeps only the `print_strn: fn(&[u8])` field: both
  built-in printers have `data = null` in the Zig, so there is
  nothing to carry. The struct is `Copy`; the two consts are
  `static`s. A `PrintT` can back a `Print` (via the `PrintSink`
  impl) by copying the static into a local first.
- `mp_print_mp_int` takes `ctx` + `types` (finding 6) — a
  deliberate signature adaptation, not a behaviour change.
- `format_float_repr` writes into the caller's 33-byte buffer
  with a NUL terminator, exactly like the Zig (max output ~23
  bytes); it `debug_assert`s finiteness — the caller
  (`print_float_core`) checks `is_finite()` first, as the Zig does.

DIVERGENCES FROM THE ORIGINAL (intentional, documented)
-------------------------------------------------------
- None in behaviour. Adaptations only: `Print`/`PrintSink`
  instead of the C `{ data, print_strn }` function-pointer struct
  (no unsafe); `mp_print_mp_int` gains `ctx`/`types` params
  (finding 6); `mp_print_str` takes a slice instead of a
  NUL-terminated pointer (same bytes, same length return);
  `mp_print_int`'s negative-base `@intCast` panic becomes a
  `try_into().expect(...)` panic.
