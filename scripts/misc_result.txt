Pairheap representation — caller evidence (as the brief required)
-----------------------------------------------------------------
- In petitpy there are NO callers: main.zig:105 and main_vm.zig:101
  only `_ = @import("memory/pairheap.zig")` to force-link the exports;
  no Zig code calls mp_pairheap_*. build.zig does not compile
  vendor/micropython_embed/py/pairheap.c (nor modasyncio.c /
  machine_timer.c, its vendor callers), so the Zig exports are the
  only implementation in the binary and nothing in the binary calls
  them.
- In vendor MicroPython the heap backs extmod/modasyncio.c (task
  queue) and extmod/machine_timer.c (timer heap): the node is
  INTRUSIVE — mp_pairheap_t is embedded FIRST in the task/timer
  struct, so the node pointer IS the object pointer (pairheap.h
  header comment).
- Safe Rust cannot do intrusive pointers without unsafe, so the port
  uses an index arena (the brief's first option). The `base`/`type`
  field of mp_pairheap_t is never read or written by
  meld/pairing/delete (verified against both the C and the Zig
  sources), so it has no Rust counterpart — the payload T carries
  whatever the caller needs.
- Panic policy (documented in code, not hidden): C segfaults and Zig
  panics on a malformed heap (dangling next, sibling chain with no
  parent tag, unknown node id). The Rust port panics with a message
  naming the violated invariant instead. A well-formed heap — built
  only by insert/meld/pairing/delete — never hits these.

Divergences / corrections found while porting
---------------------------------------------
- READER: Zig redefines the ROM notion vs vendor C, and the Rust port
  follows ZIG (the port target — it is what the running binary does):
  C says ROM ⟺ free_len == MP_READER_IS_ROM ((size_t)-1) and C's
  try_read_rom has NO bounds check; Zig says ROM ⟺ free_len == 0,
  try_read_rom returns None when free_len > 0 OR fewer than len
  bytes remain, and close frees beg iff free_len > 0 (no IS_ROM
  exclusion). MP_READER_IS_ROM is never passed anywhere in petitpy
  (grep: zero uses in src/); the only live caller,
  persistentcode.zig:465, passes free_len = 0. (persistentcode.zig:314
  comments on the same "non-ROM" reading.)
- READER: the lexer does NOT use mp_reader_t — lexer.zig:193 has its
  own pure-Zig slice Reader. The Rust reader's live consumer is the
  persistentcode .mpy loader (Phase C/D).
- RINGBUF: get16 advances iget with wrapping_add (C uint16_t wrap).
  Zig's `r.iget += 2` would panic in a debug build when size ==
  u16::MAX and iget == size - 1 (the C value there is also wrong
  vs the mathematical (iget+2)%size — a latent C corner); the port
  follows C's wrap. Unreachable from any petitpy caller (no callers
  in src/ at all).
- RINGBUF: the single-byte ringbuf_get / ringbuf_peek / ringbuf_put
  static inlines of ringbuf.h are NOT ported — they are not in
  ringbuf.zig (the port target) and no Zig caller uses them. If a
  later lane needs them, that is a separate decision.
- PAIRHEAP: Zig's pairing loop checks the tag on the advancing
  `child` POINTER itself (not on child->next) — a single-child list
  still runs one loop iteration and returns the child; the Rust
  `advance` helper preserves this (test delete_root_with_one_child
  pins it).
- No @cImport in any of the three Zig files. No extern "C" exports
  added (per brief; C-ABI export is Phase F).
