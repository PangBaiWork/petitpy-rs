Deviations / decisions (for the main agent to confirm at merge):
1. VmState.locals: Option<GcRef> ADDED (None = locals == globals),
   + eval_builtin / exec_builtin / compile_builtin Values on
   VmState, + globals_dict / set_globals_dict / locals_dict /
   set_locals_dict accessors (locals_dict() = locals.unwrap_or
   (globals)). The brief's jcb line said "only accessors, don't
   touch VmState" — but eval wiring REQUIRES the slot: the
   alternative (eval with locals==globals only) is knowingly
   wrong for corpus-tested behavior (builtin_exec.py tests
   distinct locals). Behavior is identical when None (all 938
   pre-existing C13/C14 tests still pass). load_name_ctx now
   tries locals first when Some(l) with l != globals, else
   globals; store/delete_name_ctx write into
   locals.unwrap_or(globals). The stale "LOAD_NAME is LOAD_GLOBAL
   until C12a" comment is updated.
2. Dispatch-path eval has a READ-ONLY qstr resolve
   (resolve_qstr_table_readonly, vm_eval.rs): the dispatch loop
   only has (ctx, state) and CallCtx.pool is a shared & (the C0
   design — the dispatch loop never mutates the pool). Static
   entries pass through; New bytes resolve via pool.find_strn; a
   genuinely-new name fails LOUDLY with OutOfMemory (the
   interning subsystem's own error — from_strn's only failure),
   never silently mis-resolving to "" (qstr 0). Vm::eval_exec
   (which holds &mut pool) interns correctly. Consequences,
   measured against the corpus tests: eval("1+2"), eval("x")
   with x an outer variable, exec("def foo(): ...") with foo an
   outer variable all work; exec("def bar(): ...") where bar
   never appeared as an identifier fails with MemoryError.
   The builtinevex tests pin both halves (incl. the three
   tests that must intern the name in the outer module first:
   exec_distinct_locals_corpus, exec_stores_into_globals,
   exec_globals_none_means_current_locals). Closing this gap
   for dispatch-path eval needs a CallCtx.pool mutability
   decision — changing it to &'a mut breaks the tree's
   `let pool = ctx.pool;` + resolve-closure pattern
   (obj_print_exception takes &mut ctx AND a closure borrowing
   the pool) and touches the frozen C0 interface; RefCell
   interior mutability is out (qstr_str returns &[u8] that
   cannot outlive a RefCell borrow guard, and unsafe is banned).
3. Raise propagation is the ONLY path in Rust (raise.rs): record
   pending_raise + return Err(PyRaise); do NOT print + exit(1).
   The Zig's print+exit exists only because vendor C cannot
   propagate; the longjmp branch IS propagation; the VM's top
   level prints uncaught exceptions and exits 1, so the
   observable outcome for uncaught raises is identical, and
   try/except can catch them (correct Python semantics).
4. raise.zig CORRECTION to the brief: the second comptime block
   exports the nano_mp_raise_* helpers on BOTH arms — mp_raise_msg,
   mp_raise_msg_varg, mp_raise_ValueError, mp_raise_TypeError,
   mp_raise_TypeError_int_conversion, mp_raise_NotImplementedError,
   mp_raise_type_arg ARE live under full (called by vendor MPZ,
   objint.c, modre.c). All ported.
5. runtime_utils.zig header-vs-code: the file header claims the
   C source NEVER writes *res, but the Zig code writes
   res[0] = x *% y on the non-overflow path in BOTH mul fns —
   code wins (port returns Some(product) iff !overflow).
6. opmethods.zig null-slot divergence (documented, not a bug):
   the Zig's callSubscr/callBinaryOp (mp_mirrors.zig:863-874)
   PANIC on a null slot; Rust records the generic error instead
   (ObjError::NotSubscriptable / C14's binop_unsupported) and
   documents the Zig-panics-there fact. A slot-recorded raise
   propagates untouched (obj.zig:604-605 rule).
7. compile() is BLOCKED on the missing Obj::Code: full arg
   parsing + mode validation are implemented (bad mode ->
   ValueError "bad compile mode"; non-str filename -> TypeError
   "can't convert to str implicitly"; the mode check OVERWRITES
   a pending filename error — compile("1", 5, 5) -> ValueError,
   probed), then NotImplementedError. A FunBc-as-code interim
   was REJECTED (it would misrepresent type(c) — 'function' vs
   'code'). The gap is precise: Obj::Code variant + code type
   in ROM + codeExecute over code objects (owner C15b / entry
   work). Probed: compile() WORKS on the reference binary
   (repr(c) = <>, eval(c) = 3, hash(c) works); type(code)
   ABORTS the original rc=134 (the code type pointer is null
   there — Zig panic "cast causes pointer to be null",
   mp_mirrors.zig:745); compile("1", "f", b"eval") -> ValueError
   bad mode (bytes mode does NOT match — mode comparison is by
   qstr id); compile("1", "f", "eval", 0) succeeds (extra args
   ignored, sig (3,6,false)); a non-str/bytes compile() source
   aborts the original rc=134 (the Zig passes the NULL
   str_get_data result to @ptrCast) — Rust raises the TypeError
   the polled str read records before the abort.
8. eval/exec non-buffer source: eval(123), eval([1]),
   eval(None), eval({}), eval(1.5) ALL raise OSError(12,)
   on the reference binary — stable. Mechanism: getBufferRaise
   IGNORES the mp_get_buffer failure (_ =, builtinevex.zig:33-35)
   and evalExecHelperImpl calls npy_zig_eval_exec with the
   UNINITIALIZED bufinfo; raiseBufferProtocol's TypeError
   ("object with buffer protocol required", obj.zig:179-182)
   is recorded then OVERWRITTEN by the bridge's OOM path
   (zig_compile_bridge.zig:110, mp_raise_OSError_polled
   (MP_ENOMEM=12)). Rust raises OSError(12) — the OBSERVED
   behavior, not the overwritten TypeError.
9. Protected calls have NO dyn FnMut call seam: C14's
   call_function_1/2 take only &mut CallCtx and return
   Result<Value, RtError>; testability comes from the sink
   parameter instead. protected_outcome checks pending AFTER
   the call whatever it returned (runtime_utils.zig:41-44).
10. Locals-dict pinning: eval_exec (both versions) pins the
    locals dict in roots.extra when distinct from globals —
    it is reachable ONLY through state.locals (not a GC root;
    the Zig scans thread.dict_locals as a root), and a GC
    during the body call could otherwise collect it. Same
    pattern as the module pin.
11. No stackctrl / nlr_glue / nlr_trampoline / jcb_glue modules
    (mapping table in src/runtime/mod.rs docs): stackctrl is
    no-op (STACK_CHECK=0) + GC-bound with no Rust equivalent;
    nlr_glue is @panic stubs (NOT translated into panic!) +
    mp_plat_print (already C8c's); the trampoline is setjmp/
    longjmp (PyError / pending_raise / pending_exc are the
    mechanism); jcb is the VmState accessors above.
