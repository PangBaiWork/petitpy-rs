§2. C16 stream-protocol wiring points
--------------------------------------
- StreamP / StreamReadFn / StreamWriteFn / StreamIoctlFn:
  src/objects/slots.rs:393-436 (unchanged).
- get_stream (src/support/stream.rs:108) now walks the MRO —
  header type first, then td.mro — returning the first Some
  protocol. Rationale in code: the C copies the base type's
  slots into a subclass type at creation (mp_obj_new_type,
  vendor py/objtype.c), so a subclass instance resolves the
  base's protocol; Rust user types do not inherit `protocol`
  (typecreate sets None), so the walk emulates it. Verified
  by stringio_subclass_mro_print_getvalue (both StringIO and
  BytesIO subclasses print/getvalue as their base).
- MP_EAGAIN = 11 and MP_EFBIG = 27 added next to MP_EINVAL =
  22 in src/support/stream.rs (iobase None -> EAGAIN;
  stringio_write pos overflow -> EFBIG).
- stream_read_builtin / stream_write_builtin /
  stream_readinto_builtin /
  stream_unbuffered_readline_builtin / stream_close_builtin
  / stream_exit_builtin / stream_seek_builtin /
  stream_tell_builtin / stream_flush_builtin made pub(crate)
  in src/support/stream_methods.rs so the 11-entry StringIO
  table reuses them (were private).
- locals_dict_from_entries (src/runtime/vm_types.rs:91)
  made pub(crate); used by build_io_module (all 11 names are
  static qstrs, so its panic-on-non-static-names is fine).
- The 8 stream methods in STRINGIO_LOCALS are C16's
  STREAM_METHODS bodies — no read/write loop was rewritten.
- Iteration: the VM's iternext_allow_raise_ctx
  (src/runtime/vm_rt_iter.rs:155) gained a stream branch
  BEFORE the __next__ path — if the header type's flags have
  FLAG_ITER_IS_STREAM, call C16's stream_unbuffered_iter
  (Ok(Some(v)) -> v, Ok(None) -> StopIteration, Err -> the
  recorded exception). The flag is read on the header type
  only, matching getiter's FLAG_ITER_IS_ITERNEXT check — a
  user subclass does NOT inherit the flag (C12a's typecreate
  inherits only HAS_SPECIAL_ACCESSORS), so subclass
  iteration stays a typecreate item (corpus
  io_stringio_base.py iterates a StringIO subclass — Phase E
  gate, not this lane's).

Two real bugs found by the tests, both fixed in-lane:
1. Qstr buffer protocol — write("str") failed with
   TypeError "object with buffer protocol required" while
   write(b"bytes") worked. Root cause: string literals load
   as Value::Qstr, not heap Str (load_const_str in
   src/compiler/emit/emit.rs:317 emits MP_BC_LOAD_CONST_STRING
   with a qstr, like MicroPython where a string const IS a
   qstr), and the buffer protocol only handled heap Str/Bytes.
   Fix: str_get_buffer (src/objects/strings/
   objstr_methods_c.rs) now handles Value::Qstr via
   ctx.pool.qstr_str (pool-owned slice — static table or
   leaked Box — so the raw pointer in BufferInfo stays
   valid); buffer_bytes (src/objects/containers/binary.rs)
   handles Value::Qstr the same way. This fixes the buffer
   protocol for ALL Qstr values, not just StringIO.
2. Stream iteration — `for line in StringIO` raised
   TypeError "object not an iterator". Root cause: the C's
   mp_iternext (vendor py/runtime.c:1359-1415) gives stream
   types mp_stream_unbuffered_iter when
   TYPE_HAS_ITERNEXT(type) (MP_TYPE_FLAG_ITER_IS_STREAM =
   ITER_IS_ITERNEXT | ITER_IS_CUSTOM, vendor py/obj.h:
   556-576). C16 ported stream_unbuffered_iter but nothing
   wired it into the VM's iternext. Fix: the stream branch
   in iternext_allow_raise_ctx (see §2).

§4. Not done (with owners)
---------------------------
- File/socket backends (mp_builtin_open_obj / file_io,
  socket streams): D's scope (modio.c's `open` entry is a
  parameter of build_io_module; D1 registers the module).
- Module registration into VmState.builtin_modules: D1's
  (build_io_module only returns the module; tests register
  it the way D1 will).
- IOBase FunBc delegation gap: FunBuiltin overrides work
  end-to-end through iobase_read_write (load_method_maybe +
  call_method_n_kw). A FunBc (user-defined Python) override
  CANNOT run from a StreamP fn — fun_bc_call_slot is a bare
  PyRaise stub and CallCtx has no VmState; the stub's PyRaise
  propagates (no invented error). Same gap class as C13b's
  FunBc __init__ and the collect_iterable FunBc gap. Owner:
  needs a VM-seam-aware path. Corpus io_iobase.py is a
  Phase E gate, not this lane's — it additionally needs
  print(file=...) wiring (D's sys.stdout work; print_impl
  ignores file= today).
- Subclass make_new / flag inheritance: a user subclass of
  StringIO/BytesIO does not inherit make_new or
  FLAG_ITER_IS_STREAM (typecreate sets protocol None and
  inherits only HAS_SPECIAL_ACCESSORS) — the MRO protocol
  walk covers print/getvalue/read/write, but subclass
  iteration and subclass construction through the VM's type
  call are typecreate items. Owner: C12a/typecreate.
- print(file=...) -> D (sys.stdout).
- help() module-order divergence for hash-ordered globals
  dicts: print_obj iterates MapData.entries (insertion
  order); the C iterates the raw hash table. Same set,
  possibly different order for user-module globals; ROM
  locals dicts are ordered, so their order matches.
- Type-object attribute lookup gap (PRE-EXISTING, exposed
  by this lane): `int.from_bytes(...)`, `str(int.from_bytes)`,
  `C.x` for a user class all raise AttributeError "no
  attribute '…'". The VM's LOAD_METHOD uses
  load_method_maybe_ctx (vm_rt_name.rs), which looks the
  attr up in `type`'s dict instead of the type's OWN dict
  and never consults the generic TypeData.attr slot. The
  original routes this through the `type` type's attr slot
  (mp_obj_type_attr); fixing it needs that port + switching
  VM dispatch to C14's loader (vm_tests_b.rs:442 documents
  the pending C14 rewrite). Same class as C13b's ignored
  makenew_class_attr_on_class. The e2e test
  int_from_bytes_e2e_after_classmethod_wrap is #[ignore]d
  with this reason (1 of the 4 ignored); the wrap itself is
  verified at CallCtx level (see §3 item 3).
- help() "modules" list: __main__ appears only if D1 puts
  it in builtin_modules (Zig's comes from modmain.zig).
- mp_emitter_warning has no Rust caller yet (no call sites
  in the Zig either except the code-size pass).
