## Key findings (all probed on the reference binary, 2026-11-17)

### 1. The polled-only sig check
`src/runtime/argcheck.zig:100` defines the Zig's OWN
`mp_arg_check_num_sig` — it sets `pyerr.pending_exc` and
RETURNS; callers that never poll let a later error overwrite
it. Verified: `tuple(1, 2)` → "object not iterable" (getiter
overwrites), `tuple("a", "b")` → "argument num/types mismatch"
(getiter succeeds), `tuple((1, 2), 99)` → arg-mismatch
(exact-tuple early return leaves the pending error),
`tuple(1, 2, 3)` / `list(1, 2)` → "object not iterable",
`tuple([1], 2)` / `tuple('a', 'b')` → arg-mismatch,
`array(1, 2, 3)` would be overwritten by "can't convert to str
implicitly", `memoryview(b"abc", 1)` → arg-mismatch. Same
model in Rust: record `sig_err`, continue, let a later
failure overwrite it and a later success preserve it.

### 2. Tuple hash seed is 0, NOT the reference binary's 22815552
The Zig seeds with the ROM empty-tuple object's *address*
(`@bitCast(objFromPtr(&mp_const_empty_tuple_obj))`) — a link
artifact, not a language semantic. The structure (seed +
wrapping `+%` sum of element hashes, returned through
`newSmallInt` tag-wrap) is ported faithfully; equal tuples
still hash equal. Seed-0 Rust values asserted in tests:
`hash(()) == 0`, `hash((1,2)) == 3`, `hash((None,)) == 6`,
`hash(('a',)) == 46532`, `hash((2**62-1, 2**62-1)) == -2`.
**C12 must revisit**: when the ROM singleton lands, the seed
should become the singleton's identity word so
`hash(()) == id(())` holds in Rust too.

### 3. C7 int-HASH divergence — FOUND, NOT fixed (outside this lane)
Vendor `objint_mpz.c:147-148` returns
`MP_OBJ_NEW_SMALL_INT(mpz_hash(...))` (tag-wrap, no window
check), so the reference `hash(2**62) == -(2**62)` (probed).
C7's `objint.rs:461-466` returns `new_int_from_i64(hash_mpz())`
→ `Value::int` → a heap `Int(2**62)` for out-of-window
hashes. So Rust `hash(2**62)` is currently `2**62` (heap int),
not `-(2**62)`. It cancels out at the tuple level (reference
tuple hash `seed + (-(2**62))`; Rust
`wrap_small_int(0 + 2**62) == -(2**62)` — same final value,
pinned by the tuple test with a comment). **Main agent: fix
`objint.rs` (or record it as a known divergence).**

### 4. Sort is IN PLACE with first-failure-wins
The quicksort does NOT stop on a failed comparison: the Zig's
`mp_binary_op` export wraps the call in `pyerr.bridge`, which
on error returns `OBJ_NULL` and sets `pending_exc` — the
sorter treats NULL as "not less" and runs to COMPLETION, then
the caller raises the FIRST failure. Probed partial states
(all asserted in `objlist_tests.rs`): `[3, "a", 1, 2]` →
`'str','int'`, list `[1, 2, 'a', 3]`; `[3, 1, "a", 2]` →
`'int','str'`, `[1, 'a', 2, 3]`; `[2, "a", 1]` → `[1, 'a',
2]`; `[4, "a", 3, 2, 1]` → `['a', 1, 2, 3, 4]`.
`sort(key=len)` on ints ABORTS the reference rc=134
(`fromPtr(NULL)`); Rust returns `PyRaise` for any non-None
key (documented gap — key sorting needs the VM call
machinery, C13/C14).

### 5. Original aborts Rust deliberately does NOT reproduce
- `bytearray(-1)` aborts rc=134 (`@intCast` panic at
  `objarray.zig:293`) → Rust raises `ValueError("negative
  count")` (CPython's message).
- `memoryview([1,2])` / `memoryview(123)` abort rc=134
  (uninitialized typecode at `objarray.zig:321`) → Rust raises
  the buffer-protocol `TypeError`.
- `array('i') + array('i')` and `bytearray() + bytearray()`
  abort rc=134 (`res.items.?` on a NULL buffer at
  `objarray.zig:377`) → Rust returns the empty array.
- `sort(key=len)` on ints aborts rc=134 (see §4).

### 6. Brief premises that were WRONG (corrected by probing)
- `array` has NO `tobytes`/`frombytes`/`itemsize` methods
  (probed: `AttributeError`); locals = append/extend only.
- `98 in bytearray(b'abc')` does NOT return True — int rhs
  raises bare `NotImplementedError` (the Zig checks the rhs
  kind before searching); `b'bc' in bytearray` → True,
  `'a' in bytearray` → True (str HAS a buffer).
- `array` is a MODULE, not a builtin — probes need
  `from array import array`.

### 7. Other verified semantics
- `insert` uses the raw REPR_A word (`smallIntValue`):
  False→7, True→15, None→3, qstr(id)→`(id<<2)|1`, heap→i64::MAX
  (clamp to end); `insert(1.5, x)` / `insert(2**70, x)` append.
- `remove` on a miss leaves the list unchanged (index raises
  before pop runs).
- `[1,2,3][::0]` → `ValueError("slice step can't be zero")`
  but `(1,2,3)[::0]` → NotImplementedError with the step-1
  message (list differs from tuple); array slice step != 1
  (incl. 0) → SliceStep in every case.
- `==`/`!=` dispatch: the EQ_CHECKS_OTHER_TYPE gate
  (`mp_obj_equal_not_equal`, vendor `py/obj.c:221`) explains
  `array('b')==bytes` → False while `array('b')<bytes` → True;
  bytearray/memoryview HAVE the flag (0x0408). NotEqual is NOT
  a slot op for list/tuple/array (VM inverts `==`).
- `bytearray(b'abc')[1:] = b'xy'` grows; `ba[0:1] = b'xyzw'`
  grows; memoryview slice shares the source (free += start);
  view store with len change → "lhs and rhs should be
  compatible"; view store to a read-only view → NotImplemented.
- `array('i',[1])+b'\x05\x00\x00\x00'` → `array('i',[1,5])`
  (memcpy reinterpretation); `l += (3,)` extends from ANY
  iterable; `(1,2)*0 is ()` → True; `() is ()` → True.
- `objstr.zig:3500-3660` shared locals table: C8b assembles it;
  C9b provides the array append/extend `BuiltinFn` adapters.
  `objstr_shim.c` does NOT exist (stale comment in objarray.zig).

## Implementation notes for the main agent / later lanes

  into the arena — the two borrows cannot overlap. The lane
  added `binary_set_val_bytes(ctx, tc, val) ->

  second via `copy_element_bytes` in `objarray_methods.rs`);

  pass).

  protocol required") are dropped until C13 adds `pending_exc`.
