## §1 — What was done (grounding)

The E2 gate's biggest shortfall cluster was (a) generator
collection: `list(gen())`, genexprs and `','.join(gen())` all
raised "object not iterable", and the yield-from family
(`gen_yield_from*`) died in delegation. Root causes, each
verified against the original (`~/workspace/petitpy-orig`) or
the reference binary before fixing:

1. `VmHook` trait (`src/objects/slots.rs`): the E2 `CallHook`
   was a call-only `&mut dyn FnMut`. Two separate `&mut
   VmState` closures (call + resume) hit E0499 — the wall
   E2's `vm_seams.rs` `__getattr__` comment documents. So
   ONE hook object now carries both operations:
   `call(ctx, fun, n, k, args)` and `resume(ctx, gen)`.
   `StateHook` (`vm_seams.rs`, backed by `&mut VmState`:
   call → `call_function_ctx`, resume →
   `resume_generator_ctx` iternext form + `exc_from_gen_error`)
   and `SeamHook` (adapts the ctx-only `FnMut` seams; resume
   records `TypeError("object not iterable")` and returns
   `PyRaise` — the pre-E2b error, preserved on ctx-only
   paths). `MakeNewFn`'s signature did NOT change — the
   resume capability rides the existing hook parameter through
   `type_call` → `make_new` → `collect_iterable`.
   `IterSeams.call` (iter.rs) is a separate seam type, unaffected.

2. `collect_iterable` generator arm (`objdict_collect.rs`):
   new `IterPlan::Generator(Value)`, drained via
   `hook.resume(...)`; `None` hook → `NOT_ITERABLE` (old
   behavior on ctx-only paths). This fixes `list(gen())`,
   `sorted/tuple/set/dict(gen())`, genexprs, and — via the
   `MakeNewFn` threading — `bytes(gen())`,
   `bytearray(genexpr)` (`array_extend_impl` →
   `collect_iterable`, `array_construct` / `array_make_new` /
   `bytearray_make_new` gain the `call` param) and
   `iter_items` (`objstr_a.rs`: `str_join`'s helper gains the
   hook + a `Generator` arm; new `StrError::PyRaise`, the
   `DictError::PyRaise` precedent).

3. Frame-restore fix (`vm_gen.rs`, `run_gen_frame_ctx`):
   `g.send(1)` on a new generator raised `TypeError`
   correctly, but `gen_resume` returned
   `Err(CantSendNonNone)` BEFORE running the frame, the frame
   had already been removed from `state.frames`, and the next
   resume built a dummy frame (ip=0, empty state) and executed
   garbage → `NotImplementedError: opcode`. Now the frame is
   re-inserted iff it yielded OR the post-run state is still
   New/Suspended after an early error; the dummy is never
   stored; Closed drops the frame.

4. `next()` keeps the `StopIteration` value (`vm_call.rs`,
   `call_next_ctx`): the 1-arg form went through
   `iternext_vm_ctx` + a bare `new_exception(StopIteration)`,
   dropping the generator's return value. Now it uses
   `iternext_allow_raise_ctx` (whose Generator arm builds the
   object with args via `exc_from_gen_error`).

5. `pend_throw` VM arm (`vm_call.rs`,
   `resume_via_method_ctx`, `ResumeVia::PendThrow`) — three
   bugs vs the Zig (`genInstancePendThrowImpl`,
   objgenerator.zig:324-331, `prev = self.pend_exc;
   self.pend_exc = exc_in; return prev;`): (1) it always
   returned `None` — now returns the previously queued value;
   (2) `pend_throw(None)` stored the `make_raise_obj(None)`
   `TypeError` — now CLEARS (the Zig stores `OBJ_NONE` and
   the resume ignores it, `genResumeAndRaiseImpl` line 200);
   (3) no Running check — now raises `ValueError("generator
   already executing")` (the Zig's `pend_exc == OBJ_NULL`
   guard). The same eager-conversion bug was found in
   `ResumeVia::Throw` and in the `PendThrow` store (see 8):
   both now pass/store the RAW value.

6. User-exception repr (`instance_print.rs`): root cause is
   NOT the payload — `call_type_ctx` shortcuts ALL exception
   subclasses (incl. user classes) to `exception_make_new`,
   creating a bare `Obj::Exception` with header = user class,
   while the Zig creates `Obj::Instance` + exception subobj.
   The shortcut representation is KEPT (payload checks
   `is_exception_instance` / `exception_cause` depend on
   `Obj::Exception`); the print layer now detects it:
   `is_shortcut_exception` (value is `Obj::Exception` AND its
   header type's MRO contains a ROM exception type, detected
   by `make_new == exception_make_new_slot`) prints the
   subclass name + `exception_print_inner`. Zig ground truth:
   `instance_print` (objtype.zig:1638-1685) — SENTINEL →
   subobj exception branch prints subclass name then base
   with `PRINT_EXC_SUBCLASS`; every new user type gets
   `instance_print` as its print slot at creation
   (objtype.zig:1901; Rust typecreate.rs:635).
   `repr(CancelledError())` was `<CancelledError object at
   23f>`, now `CancelledError()`.

7. Set iterators (`iter.rs`, `objdict_methods.rs`):
   `iter(iter({1,2,3}))` failed "object not iterable" and
   `list(iter({1,2,3}))` PANICKED at objdict.rs:225 ("dict
   operation on a non-dict value"). Root cause: set iterators
   are `Obj::Iterator { source: set, index: cursor, extra:
   [] }` — the same shape as a dict VIEW, and `getiter`'s
   discriminator (`extra.is_empty() && index <= 2`) matched a
   fresh set iterator (cursor 0) as a view. `getiter` now
   discriminates by SOURCE type (Dict → view, else the value
   IS an iterator); `iternext` gains a set arm
   (`set_it_next`, `SetError` → `IterError::PyRaise`);
   `as_dict_view` / `as_dict_view_it` gained the same
   Dict-source guard (that was the panic: `collect_iterable`'s
   Iterator arm misclassified the set iterator as a dict view
   and `dict_ref_of` panicked on the Set source). Frozensets
   share the `Obj::Set` payload, so the arm covers them.
   `type(iter(s))` still fails (bare TypeError, header None;
   ref `<class 'iterator'>`) — out of scope (E2 §4(p)
   iter-protocol territory; no target test calls `type()` on
   an iterator).

8. Yield-from delegation (three fixes, all in the resume
   path):
   (a) `try_instance_getiter` (`vm_seams.rs`, used by
   `getiter_vm_ctx` in `vm_rt_iter.rs`): a user instance's
   `__iter__` is a `FunBc` — it cannot run through the stub
   seams the slot path uses (`bound_meth_call_slot` has no
   runner for `FunBc`), so `getiter` silently fell back to a
   getitem iterator (`for x in MyGen()` → "object isn't
   subscriptable"; `yield from Iter()` ditto). The probe
   runs `class_lookup` with stub seams first (pure dict
   lookup — no call), so a class without `__iter__` falls
   through to the slot path's getitem fallback; with the
   hook, the `FunBc` runs. This fixes `gen_yield_from_close`
   (gen9: `yield from Iter()` + `close`), `gen_yield_from_ducktype`
   (MyGen / Incrementer / MyIter) and `gen_yield_from_throw3`,
   plus `for` over any user iterable.
   (b) Map call-seam value preservation (`vm_rt_iter.rs`,
   `iternext_allow_raise_ctx` Iterator arm): the seam
   classified a `StopIteration` from the mapped function as
   bare exhaustion, dropping its value — `yield from
   map(gen7, range(100))` lost the `444`. The seam now
   stashes EVERY raise on `state.pending_exc` and returns
   `Raise`; the arm drains it as the `StopIteration` object.
   `iternext_vm_ctx` still swallows a `StopIteration` to
   `Ok(None)` (the plain-`mp_iternext` form), so
   `for`/collection iteration is unchanged. This is the Zig's
   two-form split: `mp_iternext_allow_raise` propagates the
   object, plain `mp_iternext` swallows it.
   (c) `throw` raw-value fix (`vm_call.rs`): `ResumeVia::Throw`
   called `make_raise_obj` eagerly, so `g.throw(123)` into a
   `yield from Iter()` handed the `throw` method a `TypeError`
   object, and `g.throw(ZeroDivisionError)` handed it an
   instance. Zig (`mp_resume`, runtime.zig:1430-1453):
   `dest[2] = throw_value` — the `throw` method receives the
   RAW value; `mp_make_raise_obj` is only the no-`throw`-method
   fallback (which `resume_vm_ctx` already does). The
   conversion happens at the injection point
   (`dispatch_loop`: `make_raise_obj` when the frame does NOT
   sit on `YIELD_FROM`) — the `PendThrow` store had the same
   double-conversion and now stores the raw value too (the Zig
   stores `exc_in` as-is). The direct `gen_instance_throw`
   already passed the value raw (its doc says so).

9. `join` of a genexpr (`builtin_vm.rs` `call_join_ctx`,
   `vm_call_intercept.rs`, `VmState` handles, `vm_builtins_bind.rs`):
   `str_join` is ctx-only, so `', '.join(gen())` raised "object
   not iterable". The VM intercepts `str.join` / `bytes.join`
   by GcRef identity (the `sorted` pattern — two DIFFERENT
   `FunBuiltin` objects, one per type dict, both wrapping the
   same `str_join` fn, so two handles looked up by name in the
   str/bytes type dicts at build time). `call_join_ctx`
   collects the iterable through `make_hook`, then delegates
   to the real `str_join` on `[sep, list]` — join of a list is
   the already-working path, so non-generator input is
   byte-identical. The BoundMeth arm recurses into
   `call_function_ctx`, so the intercept sees the raw fun with
   `[sep, iterable]` for both `', '.join(x)` and
   `str.join(sep, x)`. Arity is checked here (interception
   bypasses the sig check — probed: all three arity errors are
   `TypeError: argument num/types mismatch`). Side effect:
   this also closes a Rust PANIC on `','.join()` — the direct
   `str_join` indexes `args[1]` unchecked (SIGABRT before);
   VM calls now arity-check first. The direct path still
   panics on a short call (Rust-only callers); noted in §4.

10. `objstr_a.rs` split (806 lines, over the 800 cap):
    the `StrError`/`StrExc` block (lines 37–353, verbatim)
    moved to new `src/objects/strings/objstr_errors.rs`
    (333 lines); `objstr_a.rs` is now 494 lines and
    re-exports (`pub use` for the types, `pub(crate) use` for
    `slot_raise`/`result_type`). All existing imports keep
    working. Missed test callers found along the way:
    `objstr_tests.rs` had 13 four-arg `bytes_make_new` calls
    (the E2b signature change) — all now pass `None`.

Regression tests: new `src/runtime/vm_tests_e2b.rs` (400
lines, 19 tests, `e2b_` prefix, `Fx` harness copied from
`vm_tests_e2.rs`): list/sorted/tuple/set/dict of a generator,

## §3 — Per-fix notes

- The `VmHook` design was chosen over two closures because
  of E0499 (documented in the `vm_seams.rs` header and the
  `__getattr__` comment); `MakeNewFn`'s signature is
  unchanged, so the diff touches call sites, not the
  type-call plumbing.
- The map-seam change (§1.8b) is the only behavior change
  outside generator paths: a `StopIteration` raised by a
  `map`/`filter`/`zip`/`enumerate` function now surfaces as
  the exception object through `iternext_allow_raise_ctx`
  (previously bare exhaustion). `iternext_vm_ctx` swallows
  it, so `for`/`list()`/`sorted()` are unaffected — verified
  by the 0-regression gate diffs.
- `call_join_ctx` delegates to the REAL `str_join` on a
  materialised list, so join semantics (item-type check,
  separator handling, error messages) are unchanged by
  construction; only the iterable's provenance changed.
- `subclass_native3` / `subclass_native_specmeth` flipped
  via the getiter fix (user-iterable subclasses); `builtin_zip`
  via the map-seam / collection fixes; `array_construct2`
  via the array hook threading; `string_join` via the join
  intercept; `sorted_comprehensive` / `sorted_numbers` (golden)
  via generator collection in sort inputs.
- Stdlib gains (argparse, pytest_lite) are side effects of
  generator collection / join — both suites exercise genexprs
  and `str.join` heavily; no stdlib-specific code was touched.
