Static-table sharing (the point of this lane)
---------------------------------------------
New shared module `src/qstr_table.rs` holds the single generated
table: the `include!` of build.rs's `qstr_table.rs` (the ONLY
include of it in the crate), plus `Qstr`, `N_STATIC`/`N_MAIN`/
`N_TOTAL`, and `qstr_compute_hash` — moved verbatim from
`compiler/qstr.rs` (including the ADR history comment on N_MAIN).
`compiler/qstr.rs` now re-exports them (`pub use` for the public
names, `pub(crate) use` for GEN_N_* / QSTR_STRINGS / QSTR_HASHES /
QSTR_LENGTHS), so every existing `compiler::qstr::*` path keeps
working unchanged; `QSTR_LAST_STATIC` stays in compiler/qstr.rs
(it is a .mpy encoding boundary, compiler-side; mpy.rs keeps its
own copy in sync as before). `runtime/qstr.rs` imports from
`crate::qstr_table` directly — the runtime never imports from the
compiler. `build.rs` untouched: the header is still parsed exactly
once, at build time.
`src/runtime/mod.rs` (new) + `src/lib.rs` (adds `pub mod qstr_table;`
and `pub mod runtime;`).

Check-script finding: the vendored header INTERLEAVES QDEF0/QDEF1
lines (62 QDEF0 lines sit after the first QDEF1 line), so id order
is NOT file order — it is all QDEF0 in file order, then all QDEF1
in file order, exactly as build.rs collects them. The first version
of check_qstrrt_table.py parsed in raw file order and failed with
real-looking mismatches (e.g. runtime[173] `__and__` vs header
`<setcomp>`); fixed to the statics-then-mains order, then PASS.
