### P4 — import os.path 报错名（DONE, 0cbebe1）
- 机制（triage 假设“在 parent 分支拼名字”是错的）：`import os.path`
不是 import-loader 拼名，而是 PEP 562 模块 `__getattr__`：
`modos.zig:208-215`（`py_os_getattr`）：`os.path` 时 import
`os_path`（失败即传播——故 REF 报 `ModuleNotFoundError: No
module named 'os_path'`），其它属性 import `os_ext`（失败吞
掉、pending 清掉），查到属性返回，否则 `AttributeError("no
attribute '%q'")`。
- Rust 已有 `os_getattr_stub` + `os_getattr_ctx`
（modos.rs:604-693），VM loader `load_method_maybe_ctx`
（vm_rt_name.rs:186）也已走模块 `__getattr__`，但
`process_component`（builtinimport.rs）用的是 C14 的
`load_attr_maybe`（import_search.rs:294），其 AttrFn 适配器
不带 `__getattr__` 缝合，于是落到 "not a package" 报错。
- 修（builtinimport.rs 唯一文件，+20/−3）：`process_component`
改用 `load_method_maybe_ctx`，AttributeError 按 Zig 的
`loadAttrMaybe`（import_search.zig:92-98）吞掉；其它 raise
原样传播（`os_path` 的 ModuleNotFoundError）。
`exception_match` 需 `Value::Heap(state.exc.attribute_error)`
（第一次传裸 GcRef 报 E0308，已修）。
- 验证：有 `os_path.py` 时 `import os.path;
print(os.path.join('a','b'))` → `ok a/b` rc=0；无时
`ModuleNotFoundError: No module named 'os_path'` rc=1；
`import os.nonexistent` → `ModuleNotFoundError: No module
named 'os.nonexistent'; 'os' is not a package`（与 REF 一致——
REF 的 `__getattr__` 对 nonexistent 报 AttributeError，被吞
掉后触发 "not a package"）；`os.nonexistent` 属性访问 →
`AttributeError: no attribute 'nonexistent'`（双边一致）。
- 探针：~/workspace/g5_probe/probe_p3.py 的 p4_ospath 用例。

### P3 — 文件写缓冲（DONE, 8dbdc06）
- 机制（读原版确认）：`npyFileWrite`（file_io.zig:160-176）
调 libc `fwrite(buf, 1, size, fp)`；CLOSE 时 `_ = fclose(fp)`
（~214-225），返回值丢弃，flush 错误在 close 处被吞。
Rust 之前直写 `std::fs::File`，故 /dev/full 在 write 时
即报 OSError 28。
- 修：`FileHandle::Owned` 改为
`Rc<RefCell<BufWriter::with_capacity(4096, file)>>`
（4096 = glibc 默认文件缓冲大小，value_data.rs）；
`fileio_read` 先 flush 写缓冲（libc `FILE*` 换向 flush；
flush 失败在此处报出，如原版 `fread` 经 `ferror` 报出）；
`BufWriter::seek` 先 flush（同 `fseek`）；open_impl 构造处
包 BufWriter（objfileio.rs）。
- 附带真 bug（同文件）：SEEK ioctl 把新偏移写进
`state.offset` 而非 `state.result`——`stream_seek`
（stream.rs:277）读的是 `result`，故所有文件 `seek` /
`tell` 返回 0（探针 p3e：REF tell 5，Rust 0）。现写
`state.result`，与 StringIO 后端（objstringio.rs:423）
与 stream fixture（stream_fixture.rs:104）一致；fileio
seek 测试原断言 `st.offset` 是在钉这个 bug，已改为断言
`st.result`（objfileio_tests.rs）。
- 探针 ~/workspace/g5_probe/probe_p3.py 9 用例全 SAME
（p3a 小写 /dev/full、p3b 5000 字节写 /dev/full、p3c
写读往返、p3d flush 到 /dev/full、p3e tell、p4_ospath、
p5a/b/c）。`os.write` 直接路径 triage 已断言不受影响
（G5 未重探——主 agent 验收时可顺带确认）。

### P9 — stress 路径 finaliser 延迟（低价值，未做）
- 现状：stress 收集在 `GcArena::alloc_inner` 内触发
（gc.rs:572-576），只调 `collect_inner`，pending
finalisers 列入 `pending_finalisers`；drain
（`drain_pending_finalisers`）只在显式 `gc.collect()` 后
经 `call_gc_collect_ctx` 跑（有 `&mut CallCtx` +
`&mut VmState` 才行）。
- 为何不动：原版在任意 collect 内同步跑 finaliser
（gc.zig:298 `runFinalisers`，全局 VM 状态，`__del__`
可任意调）；Rust 的 collect 在 arena、drain 在 VM，
stress 点（`alloc_inner`）只有 `&mut GcArena` +
`&RootSet`，`CallCtx::alloc` 有 ctx 无 VmState。修它要么
把 VmState 穿进每个 alloc 点（树级改动），要么在 VM 主
循环加定期 drain 点（热路径 + 重入风险）。可观察性极低：
需 NPY_GC_STRESS 下文件失活后又无显式 collect 才漏关
fd。留给后续 lane。
- triage P4 条目机制已证伪（见 §1 P4）——triage 文档待
主 agent 在 G5 合并时同步更正。

### P14 — 管道 stdout 缓冲（机制已定位，改动面大，follow-up lane）
- 范围探针 ~/workspace/g5_probe/probe_p14.py：p14a `-c`、
p14b 脚本、p14d 文件重定向、p14e REPL——REF 均缓冲
stdout（行在 2s 后同到），Rust 直写；p14c stderr 双边
立即到（stderr 无缓冲）。
- 机制（已定位）：REF 的 `mp_sys_stdout_obj.fp` 就是 libc
的 `stdout` FILE*（file_io.zig:486，
`mp_sys_stdout_buffer_obj` 同）；`npyFileWrite` 走
`fwrite`，故 glibc stdio 缓冲：管道时全缓冲 4096 字节，
tty 时行缓冲。`print()` 走 `MP_PYTHON_PRINTER` =
`mp_sys_stdout_print`（`{&mp_sys_stdout_obj,
mp_stream_write_adaptor}`，full_stubs.zig:58-62）。
有 sink 时 bypass 缓冲，`output.write(1,...)` 立即
（file_io.zig:166-169）。Rust 侧 `FileHandle::Stdout`
走 `std::io::stdout().write_all`（objfileio.rs:178），
Rust `Stdout` 是 LineWriter，见换行即 flush，故管道下
直写。
- 修的形状（follow-up lane）：`FileHandle::Stdout` 加
4096 字节缓冲，满即 flush；`is_terminal()` 时见换行
flush（行缓冲）；有 sink 时 bypass；退出时、
`sys.stdout.flush()`、`print(flush=True)` 时 flush。
触点：FileHandle::Stdout 变体、fileio_write/flush、
退出路径（embed_exec/main/REPL）。P3 同机制的
BufWriter 只盖了 `Owned` 文件，未盖 stdio——P14 与 P3
是同一缓冲层的两半。
- 注：P8 修完后 finaliser 打印走 fd 1（stdout），故也进
同一缓冲问题域——P14 lane 需一并确认 drain 打印在管道
下的时序。
