1:1 function mapping (C/Zig -> Rust)
------------------------------------

- mp_format_float(f, buf, buf_size, fmt, prec, sign) -> i32
    -> format_float_into_buf(f: f64, fmt: u8, prec: i32, sign: u8,
       buf: &mut [u8]) -> i32   (same contract: returns bytes written
       excl. NUL, incl. sign; NUL-terminates; never writes past

       brief's rule)

- mp_prepend_zeros -> prepend_zeros (private)

Return-value / truncation conventions (verified by probe + unit tests)
-----------------------------------------------------------------------
- Return = bytes written excluding NUL, including sign; NUL written.
- %f with a huge exponent switches to %g when it would not fit
  (1e300 'f' 6 buf 33 -> "1e+300"; buf 512 holds the 'f' form, 308
  chars: "1" + 300 zeros + ".000000").
- max_digits / trail_zeros clamped to the buffer; prec 100 'f' in a
  33-byte buffer truncates to 31 digits + NUL.
- prec < 0 defaults to 6; prec 99 = optimal-repr path (prec -> 19,
  max_exp_zeros 16); unknown fmt byte behaves like 'e' (else branch).
- inf/nan: case follows fmt bit 0x20 ('F'/'E'/'G'/'X' -> upper);
  negative NaN sign ignored (C !isnan guard); sign '+'/' ' prepended
  even for inf/nan; -0.0 keeps its sign.

Divergences / findings (all verified empirically, not assumed)
--------------------------------------------------------------
1. THE BIG ONE — petitpy's mp_parse_float_internal is ZIG, not vendor C
   (src/frontend/parsenum.zig:328, `export fn mp_parse_float_internal`).
   The scan loop / accept_digit / exponent bookkeeping are identical
   to vendor parsenum.c, but the final value comes from libc strtod
   (correctly rounded) on the scanned text, falling back to
   mp_decimal_exp only when strtod does not consume the whole text or
   the text is >= 128 non-'_' chars. Vendor C always uses
   mp_decimal_exp, which is off by an ulp at times (the Zig comment
   cites "2.2250738585072014e-308"). The Rust port follows the Zig
   version via Rust str::parse::<f64> (also correctly rounded, so it
   agrees with strtod on every decimal string), with the same
   fallback. A port using only the vendor C parse fails 110/3440
   probe cases in the last digit; with the Zig semantics it is
   3440/3440. mp_decimal_exp itself IS algorithm-identical in C and
   Zig (bit-field add mod 2048, pow(5, k)); only the parse-back differs.
2. The pure-vendor-C harness (harness_zig) is NOT a valid oracle for
   petitpy: the binary links the Zig parsenum, so vendor-C and binary
   disagree in the last digit on 13/3440 high-precision cases
   (123456789.123456789 'g' 99 / 'f' 100: vendor ...684, binary ...679;
   DBL_MAX 'g' 99 / 'f' 100: vendor ...3156, binary ...3158).
   Fix: harness_ziglike (vendor C formatfloat.o + parsenum_ziglike.c,
   a C reimplementation of the Zig parse-back), cross-checked 2940/2940
   against the binary on every binary-reachable case. The generator
   now uses harness_ziglike; harness_zig is kept in
   build_charharness.sh only as a documented wrong-oracle reference.
   The 13 vector lines changed accordingly (old SHA e788069b...).
3. Subnormal UB: mp_decimal_exp shifts the exponent field directly,
   wrong for subnormals (exp field 0 -> setting it materialises the
   implicit leading 1); the mantissa then overflows u64 and the C
   cast (u64)(mantissa_f + 0.5) is UB. The shipped formatfloat.o
   (both copies in the reference build's .zig-cache) contains
   vcvttsd2usi -> u64::MAX for out-of-range inputs. A gcc-compiled
   copy resolves the same UB to mantissa 0 and is NOT a valid oracle.
   Rust c_f64_to_u64 reproduces vcvttsd2usi exactly (NaN/negative ->
   u64::MAX, else saturating `as u64`); unit test
   c_f64_to_u64_vcvttsd2usi pins it. Subnormal outputs verified vs
   the binary (5e-324 '%.6e' -> "0.955161e-323", '%g' ->
   "9.55161e-323", '%.17g' -> "4.467440737095516e-323").
4. Approximate last digits vs CPython — by design, ported exactly
   (the vendor APPROX algorithm, not CPython's correct rounding).
   All verified against the reference binary (or harness_ziglike
   where the binary cannot reach the case):
   - 1.23456789012345678 'g' 17 -> "...4566" (CPython "...4567")
   - 1.23456789012345678 'f' 17 -> "...45660" (CPython "...45669")
   - 1.23456789012345678 'f' 19 -> "...4566000"
   - sqrt(2) 'g' 17 -> "...952" (CPython "...951")
   - sqrt(2) 'f' 17 -> "...9520" (CPython "...9515")
   - DBL_MAX 'g' 17 -> "...3158" (CPython "...3157")
   - 2.2250738585072014e-308 'g' 17 -> "...2012" (CPython "...2014")
   - 0.5 'f' 0 -> "0": dichotomic-search tie-break prefers mantissa 0
     (|0-0.5| == |1-0.5|, 0 % 10 == 0); CPython also "0".
   - 1e300 'f' 6 buf 512 -> "1" + 300 zeros + ".000000" (308 chars),
     NOT the exact integer digits 1000000000000000019884624838656...
   - 1e16 'g' 99 -> "1e+16" (harness_ziglike), not "10000000000000000".
   Process note: 10 of my hand-written unit-test expectations were
   initially CPython-based guesses and were wrong; every one was
   corrected only after checking the binary/harness — none was
   flipped to match the code unexamined. The probe battery is the
   guard against this class of mistake.
5. Config (verified from source, not assumed): MICROPY_FLOAT_IMPL =
   DOUBLE, MICROPY_FLOAT_FORMAT_IMPL = APPROX
   (port/mpconfigport.h:209-210); mp_large_float_t = f64,
   mp_large_float_uint_t = u64, MP_FLOAT_EXP_OFFSET = 1023,
   MANTISSA_MAX = 0x1999999999999998, MAX_EXACT_POWER_OF_5 = 22.
   Reference C flags: -std=c99 -DNDEBUG -fno-sanitize=undefined
   -fno-common -DPETITPY_CONFIG_FULL=1, Debug -O0. -DNDEBUG means
   the C asserts are dormant in the reference build; the Rust port
   keeps the equivalent checks active.
6. Callers (read, not ported): mpprint.zig:36 (extern declaration),

   comment (repr intercepts prec==99 + 'g' + finite and uses
   formatFloatRepr/Ryu because vendor mp_format_float "gets the last
   digit wrong (sqrt(2) ends in 952, 5e-324 prints as 1.8e-323)").
   C callers: mpprint.c mp_print_float (buf[36], passes 33),
   objfloat.c:113 (repr 'g' 99), objcomplex.c:52,58 (real/imag 'g' 99),

Harness notes (test tooling, not deliverable code)
-------------------------------------------------
- /tmp/charness is a build artifact (rebuilt by
  scripts/charharness/build_charharness.sh); the script is committed,
  the binaries are not.
- The generator's binary oracle runs the reference binary with `%`
  formats (prec 99 'g' excluded — binary intercepts it for repr).
- Probe sign encoding: '0' none, '+' plus, 'S' space; harness main.c
  accepts 'S' (a literal space cannot be an sscanf token).
- Generator bug fixed during work: bits_of initially used
  little-endian hex, misread by the probe/harness (e.g. -0.0 became
  6.3e-322); fixed to big-endian integer hex. It also initially
  dropped inf/nan on a repr-check bug (compared against the
  constructor expression instead of repr(v)); fixed, 0 dropped now.
