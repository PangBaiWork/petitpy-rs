DIVERGENCES FROM THE REFERENCE (deliberate, recorded)
-----------------------------------------------------
D1. COMPLEX IS IMPLEMENTED, THE REFERENCE ABORTS ON IT.
    objcomplex.c is NOT compiled by build.zig; full_stubs.zig provides
    @panic stubs for mp_obj_new_complex / mp_obj_complex_binary_op /
    mp_obj_complex_get / mp_type_complex. Probed 2026-11-18: complex(3,4),
    complex(1), complex(), complex('1+2j'), complex(1,2)+complex(3,4),
    complex(1,2,3) ALL abort the reference binary rc=134 (stack trace
    0x145db64). This lane implements complex properly from the vendor C
    code (the Zig's "F4 target"), following the precedent of C9b/C11
    abort-divergences. Rust returns the value; the reference aborts.
    The complex literal load failure is NOT a divergence: print(1j) and
    print(3+4j) raise ValueError "invalid syntax for number" on the
    reference AND in Rust (loader calls parse_num_float(allow_imag=false)).
D2. HEAP-INT NEGATIVE-BASE POWER: (-(2**70)) ** 0.5 ABORTS on the
    reference (rc=134) but raises ValueError "complex values not
    supported" in Rust. Cause: the Zig floatOpPrecheck fires only on
    the small-int-lhs and float-lhs paths (runtime.zig:705/732); a
    heap-int lhs goes through the generic loop -> int slot -> vendor
    float op -> POWER arm delegates to the stubbed complex op -> abort.
    (-(2**62)) ** 0.5 is SMALL_INT_MIN, so the precheck fires and the
    reference raises ValueError there. Rust applies the precheck
    uniformly inside float_binary_op, so the heap-int case raises the
    same ValueError instead of aborting. Probed: (2**70)**0.5 =
    34359738368.0, (-(2**70))**2 = exact int 1393796574908163946345982392040522594123776,
    (-(2**70))**-1 = -8.470329472543003e-22, (-(2**70))/0.0 ->
    ZeroDivisionError.
D3. Float raises follow the Zig floatOpPrecheck semantics, not vendor
    C's (vendor C raises by longjmp, uncatchable; the Zig raises
    catchably first). Probed catchable: try: 1/0.0 except ZeroDivisionError
    prints "caught"; try: (-8.0)**0.5 except ValueError prints "caught-ve".
    POWER precheck (implemented inside float_binary_op, Rust propagates
    catchably everywhere): lhs==0 && rhs<0 -> ZeroDivisionError with NO
    isinf exclusion (0.0**-inf raises); lhs<0 && rhs != trunc(rhs) ->
    ValueError, where NaN counts ((-8.0)**nan raises, since
    nan != trunc(nan)) and inf does NOT count ((-8.0)**inf = inf).
    MICROPY_PY_MATH_POW_FIX_NAN defaults 0 and the port does not
    override it; Rust powf already gives 1.0**nan = 1.0 and nan**0.0 = 1.0
    (IEEE), so no POW_FIX_NAN branch is needed.
    Probed inf/nan power: 0.0**-inf -> ZeroDivisionError,
    (-8.0)**nan -> ValueError, 1.0**nan = 1.0, nan**0.0 = 1.0,
    2.0**nan = nan, nan**2.0 = nan, (-8.0)**inf = inf, 2.0**inf = inf,
    0.5**inf = 0.0, (-1.0)**inf = 1.0, 0.0**nan = nan.

    layout [pos..., kw_key, kw_val, ...]. float(x=1) parsed the KEY

    of the polled TypeError. Fix: branch on n_pos =

    complex_make_new, AND int_make_new (identical latent bug in C7's
    code — int(x=1) raised ValueError "invalid syntax for integer").
    bool_make_new is unaffected (its branch doesn't parse the key).
    str_make_new_slot uses split_kwargs (correct already). Tests:
    float_make_new_errors, int_and_complex_kwargs_raise_mismatch.
B2. int * str/bytes/tuple/list was binopUnsupported (pre-existing gap,
    proven NOT a regression of this lane: the int delegation checks
    float/complex only, and the removed vm_rt block matched Float/
    Complex rhs only). Vendor objint.c:381-394 extra_cases delegates
    MULTIPLY with SWAPPED operands and the PLAIN op via call_binary.
    The generic loop's reverse path CANNOT do it: no ReverseMultiply
    case exists in the str/tuple/list slots (vendor or Zig). Only plain
    Multiply delegates (inplace retries as plain). A delegated raise
    travels on CallCtx.pending_raise (C6 convention — call_binary maps
    it to NotImplemented); returning NotHandled with it set lets the
    runtime loop propagate it. Tests: int_float_interop
    (2*'ab'='abab', 2*[1]=[1,1], 2*(1,)=(1,1)).
B3. float_precheck_int in vm_rt.rs used rhs_f.fract() != 0.0 — wrong
    for inf (fract(inf) is NaN != 0, so (-8) ** inf would raise
    ValueError; the reference returns inf, probed). Changed to
    rhs_f != rhs_f.trunc() (the Zig's test, runtime.zig:493).
    Behaviorally identical at its only call site (integer rhs always
    has fract 0); the fix aligns the helper with the Zig for future
    float-rhs callers.
B4. load_method_maybe_ctx attr fallback (vm_rt_name.rs): the VM's
    LOAD_ATTR path hardcoded attr fns for fun_bc/gen_wrap/bound_meth/
    closure + module/exception by payload and NEVER consulted
    TypeData.attr generically, so complex .real/.imag did not load.
    Added a generic fallback (only when the hardcoded dispatch found
    nothing, so no attr fn runs twice). The Zig's mp_load_method_maybe
    consults the type's attr slot for every type.
