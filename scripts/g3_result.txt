§4 — leftovers / known deviations (all probed on REF 2026-11-19)
  (a) Raising __eq__ is state-dependent on REF and has no uniform
  rule; the probe-level discard (probe_equal) matches REF exactly
  on the load case (KeyError) and on all well-behaved acceptance
  probes, and deviates only in the raising corner:
    - `A() in d` / `d.get(A())` with a raising __eq__: REF
      propagates the ValueError; Rust returns False / the
      default (discarded in the probe).
    - Second store `d[A()] = 'y'` (dict already holds an A key)
      with a raising __eq__: REF raises TypeError
      "unsupported type for operator"; Rust stores silently
      (probe reads not-equal, inserts a second entry).
    - `s.add(A())` (set already holds A) with a raising __eq__:
      REF raises TypeError; Rust inserts silently.
    - `A() == A()` with a raising __eq__: REF propagates the
      ValueError (the VM polls the pending raise after the op);
      Rust returns False with a stale stash — the same swallow
      shape lives in E2d's `==` path (obj_equal_not_equal's
      in-loop `Err(PyError::PyRaise) => {}`), OUT of G3 scope.
      A follow-up lane could surface it by draining the hook
      stash after a successful `==`/`!=` and re-raising — the
      probe_equal fix shows the shape.
  (b) Pre-existing module-doc inaccuracy found while testing H5:
  objset.rs claims `s.add([2])` raises "but `s == {[2]}`" — as
  a runnable program that equality itself raises TypeError on
  REF too (the comparison re-hashes the element; even two
  quirk-built sets can't compare). The quirk IS observable via
  len(s)==1 / list(s)==[[2]] / repr(s)=='{[2]}' (all probed on
  REF, all asserted by g3_h5_set_add_unhashable_quirk). The
  module doc should be corrected to the len/list/repr wording.
  (c) `str(KeyError(instance))` still shows the ctx-only
  `<Color object at N>` fallback (exception print slot has no
  hook) — H10/G4's item, untouched here.
  (d) Dict-subclass `__missing__` through the ctx-only slot
  seams (instance_subscr_slot) still yields a bare TypeError
  instead of KeyError — only the VM path (try_instance_subscr)
  was fixed by H4; no gate coverage for the slot path.
  (e) H9 (import_from FunBc fallback) low value, G4 to decide.
  (f) Tooling notes (recurring, for the next lanes): the
  panic-strategy `abort` vs `unwind` mismatch on bin-test
  compiles and the stale-rlib link failure (undefined symbols
  e.g. Vm::new) are the same pre-existing cargo artifact
  race (cdylib/staticlib/rlib output-filename collision);
  every occurrence in this lane was fixed by a plain rerun
