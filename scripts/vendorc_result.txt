DIVERGENCES FROM CPython (ported exactly, oracle-modelled in the generator)
-----------------------------------------------------------------------------
- pow: 0 when base == 0 or exp < 0; 1 when exp == 0 (except base == 0 -> 0).
  CPython: 0**0 == 1, 2**-1 == 0.5. Verified on the reference binary:
  0**0 -> 1 (small-int path, not mpz), pow(2,-1,5) -> 0.
- pow3: 0 when base == 0, exp < 0, or mod == 1.
- hash: u64 truncation of the magnitude (negated if negative), NOT
  CPython's modular hash. hash(2**70) == 0 in mpz, 512 in CPython
  (verified on the reference binary).
- as_int_checked: rejects -2**63 (returns None) even though it fits
  in i64 — the C overflow check trips on its second digit.
- set_from_float: floats in [-2, -1) map to +1 (the adj_exp == 0
  branch calls mpz_set_from_int(z, 1), resetting the sign). Excluded
  from the probe battery; covered by unit test
  set_from_float_negative_one_to_two_quirk. Unreachable via int(float)
  in the reference build (objint.c takes the small-int fast path).
- Negative zero: set_from_str with neg=true sets neg before parsing,
  so "-0" and "" with neg=true produce neg=true, len=0; cmp compares
  sign first, so -0 < 0. Ported exactly; the probe compares value and
  sign separately (cmp-based PartialEq would reject the faithful state).
- as_bytes: for NEGATIVE values whose magnitude needs more than
  `length` bytes of digits (4 * len(digits) > length), mpz returns
  ok=false even when the value fits the signed buffer, because the
  two's-complement sign-extension bytes (0xFF) fail the C's
  "remaining bytes must be zero" check. Verified on the reference
  binary: (-2**70).to_bytes(9, 'little') -> OverflowError: buffer too
  small, while (2**70).to_bytes(9, 'little') works and CPython
  succeeds for both. Same quirk: (-2).to_bytes(1) is false at the
  mpz level (low byte 0xFE is still written). The caller
  (mp_obj_int_to_bytes_impl) only ever passes as_signed = neg.
  The generator's oracle simulates the C directly and asserts CPython
  agreement only where it applies.
- as_float: Horner accumulation in double (most significant digit
  first). The generator reports 0 disagreements vs float(x) in the
  battery, so this agrees with CPython wherever tested.

DESIGN DECISIONS (all documented in code comments)
---------------------------------------------------
- Aliasing: C allows dest == operand; Rust borrows forbid it at the
  API boundary, so free *_inpl functions require a distinct dest;
  *_assign methods and internal loops clone first (as C's
  mpz_mul_inpl does on aliasing). Observable behaviour identical.
- Error paths: the C asserts on a zero divisor (divmod) / zero
  modulus (pow3); Rust returns Err(PyError::PyRaise). Real callers
  raise ZeroDivisionError / ValueError (objint_mpz.c checks first).
- set_from_int(i64::MIN) / set_from_ll(i64::MIN, true) use
  unsigned_abs() (same bits as C's wrapping -val, defined).
- mpn functions are slice-based with no aliasing; callers clone
  where C relies on in-place aliasing (not_inpl, shr round-up,
  pow/pow3 loops).
- mpn_div norm_shift==0 is safe because of the u64 casts in the C
  (e.g. (n as u64) >> 32 == 0); the Rust port mirrors those casts.
- shl_inpl/shr_inpl take rhs: u64 (mp_uint_t); mpn_shl/mpn_shr
  require n > 0 (debug_assert; callers only call with rhs != 0).
- Inherent-method naming: inherent methods named add/sub/mul/
  bitand/bitor/bitxor/neg/not/shl/shr were REMOVED. They collide with
  the std::ops trait methods, whose by-value `self` receiver matches
  at an earlier method-resolution probe step than an inherent
  `&self` method, so `a.add(&b)` resolved to the trait and failed
  type-checking. The public API is the free *_inpl functions +
  operator traits + non-colliding inherent methods (abs, pow, pow3,
  divmod, add_assign, sub_assign, mul_assign). The trait impls call
  the free functions directly.
